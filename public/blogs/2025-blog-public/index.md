# 从一个博客，到现在这坨东西

这个项目最开始只是一个博客。

当时想法也很简单，找个地方放文章、项目，还有自己平时折腾出来的一些东西。然后不知道从什么时候开始，各种各样的东西逐渐塞进来了。

图片压缩、视频压缩、Markdown 查看器、人脸打码、OCR、密码生成、文件传输、Git / SVN、Codex Session……

到现在这个不应该叫做博客了，应该升级成为个人工具箱了。

但项目名都叫 `2025-blog-public` 这么久了，改起来可能还需要换Vercel、EdgeOne、Netlify那边的很多变量。

所以暂时还是博客。

---

## 最开始其实没想这么多

这个项目最开始就想的是我需要一个东西用来记录，毕竟学习的东西太多，然后就像一个备忘录一样的东西，放上我的经验以及踩坑历史等等，以前是写CSDN上面的，也是火过几篇文章。

但是我觉得没有什么项目归属感，就相当于只写了文章一样，或者说感觉有点不够“自由”，所以就决定建一个个人站，上面放自己的东西。

建站起来也是非常快的，我很久之前就购买了服务器和域名，当时就只想着倒腾倒腾，倒是在建站方面节省了很多的时间，起码域名、备案、服务器都有了。

但是事实上我没用有自己的服务器，自己的服务器维护起来考虑的就多了，但是作为一个静态网站（目前看来是这样的，说不定未来就不是了），我们直接上Vercel、EdgeOne，方便快捷还不需要维护，简直是量身定做，只需要修改然后推送上去直接就自动一键部署，深得我意。

# 博客本身反而是现在最简单的一层

虽然整个项目越来越复杂，但文章这一块我一直没动。

没有评论，没有文章数据库。

没有文章编辑器。

甚至连网页后台都没有。

文章就是 Markdown，其他内容基本就是 JSON。

改内容：

```text
改文件
↓
提交
↓
推送
↓
部署
```

就完事了。

站点现在主要还是 Next.js 16、React 19、TypeScript 和 Tailwind。

我之前其实也想过，要不要搞一个后台，可以直接在线写文章、编辑项目、上传图片。

后来想想完全没必要。

我本身就在写代码，不需要在线写，而且AI发达，说不定AI写更快（当然我还是更倾向于手搓文章，AI写的一直和我的想法对不到一块并且太“AI”了），一般是AI结合手搓写文章。

为了一个我自己用的网站，再做用户系统、权限、数据库、编辑器、版本管理，属实有点为了后台而后台。

所以这一块反而一直保持得比较原始。

但是好维护。

# 真正越做越离谱的是 Toolbox

现在我觉得整个项目最有意思的部分，其实已经不是博客了。

而是 Toolbox。

目前工具箱里面已经有：

* 快传
* 图片/视频压缩
* ZIP 打包
* Markdown 查看器
* 人脸打码
* 图片 / PDF 文本提取
* 密码生成
* Git / SVN 版本控制器
* Codex Session 解析器

看起来挺杂，实际上也确实挺杂。

这些工具之间并没有什么伟大的产品逻辑。

唯一比较统一的地方就是：

**我尽量不想把用户的东西上传到服务器。**

因为我们根本没有服务器。。。。。。。

比如你压一张图。

为什么非得：

```text
图片
↓
上传服务器
↓
别人压缩
↓
再下载
```

浏览器明明自己就能干。

密码生成更不用说了。

OCR 现在浏览器也能跑模型。

视频有 WebCodecs。

文件可以通过 File System Access API 流式读取和写入。

GitHub 有 REST API。

局域网传输有 WebRTC。

现在浏览器的能力其实已经比很多人印象里强得多了，浏览器内核代码都超过一些操作系统了，我上回看Chromium 4000W行，Linux Kernel才3000W行，如果只算核心的逻辑甚至操作系统才几百万行（当然我说的内核，真正的完整的比如Windows 11大概在7000W行左右了），甚至还有开源项目在浏览器虚拟出一个操作系统出来。

所以这个 Toolbox 后来逐渐形成了一个很简单的原则：

> **浏览器能自己干，就别上服务器。**

# 图片压缩还算正常，视频压缩开始上强度

图片压缩没什么特别好讲的。

真正让我开始重新思考“网页工具到底能做到什么程度”的，是视频压缩。

最开始我也考虑过 FFmpeg WASM。

很经典的方案。

问题是当文件变成几 GB 以后，就存在瓶颈了，我们目标是能够压缩超过16G以上的视频（虽然可以分段压缩）。

如果整个文件先读进内存：

```text
8GB 视频
↓
Blob
↓
WASM 文件系统
↓
解码
↓
重新编码
↓
再生成一个几 GB Blob
```

浏览器看了都想跑路。

所以后来的思路就完全变了。

不再把整个文件搬来搬去。

直接读文件，直接编码，直接写硬盘。

现在视频压缩的核心是 Worker + 流式输出，通过浏览器文件系统接口直接写到用户选择的目标文件。

甚至还做了分段并行。

简单理解就是：

```text
视频

├─ 第 1 段 → Worker 1
├─ 第 2 段 → Worker 2
├─ 第 3 段 → Worker 1
├─ 第 4 段 → Worker 2
...

↓
按原顺序重新合并
↓
直接写文件
```

这里最大的取舍其实不是用了什么库。

而是我后来基本放弃了“所有浏览器都要完美支持”这个想法。

如果想处理真正的大文件，那么 Chrome / Edge 这些 Chromium 浏览器提供的 File System Access API 很重要。

Firefox 不支持？

那就不支持。

有些东西如果为了兼容所有浏览器，最后只能把功能砍成玩具，我觉得反而舍本逐末了。

当然这个功能可能我们还会继续升级体验，毕竟就我还是要经常用的，比如视频音频分离啊、裁剪啊这些未来可能都会支持，毕竟覆盖一些小的功能吧，大的就上剪映了。

# ZIP 这个东西看起来简单，做起来比我想象的烦多了

ZIP这个功能是我经常遇到的问题，我经常需要将代码打包给AI分析（让AI从全局来看我的代码），但是Bandizip就不能做到那种目录选择，比如一个项目要打包分析，但是下面比如有一层是依赖或者其它的不需要打包，就不好弄，所以有了这个工具，这个工具能够对文件夹和文件进行细致的选择，那些需要打包那些不需要，我经常使用。

ZIP 一开始我觉得：

选个目录。

压缩。

保存。

结束。

然后很快就发现完全不是这么回事。

比如一个代码项目：

```text
项目
├─ src
├─ public
├─ node_modules
├─ .git
├─ .next
└─ ...
```

如果用户刚选目录，你就直接把几十万个文件全部递归扫描一遍，浏览器直接开始干苦力。

所以现在一些目录，比如：

```text
.git
.svn
node_modules
.next
dist
build
target
```

默认不会立刻深入扫描。

先把目录句柄留着。

用户真的展开或者选择它的时候，再进去读。

另外 ZIP 写入也是一个文件一个文件来。

没有为了“看起来快”开一堆并发。

因为真正压一个大目录的时候，内存稳定比那一点点理论吞吐重要多了。

还有一些奇怪问题。

比如文件扫描完以后，在你真正开始写 ZIP 之前被别的软件改掉了怎么办？

现在会检查文件大小和修改时间。

不一样直接报错，让你重新扫描。

再比如某一个文件突然没有权限读了。

以前这种错误很容易把整个 ZIP 干废。

现在是：

```text
A.jpg ✔
B.txt ✔
C.log × 没权限
D.mp4 ✔
E.md ✔
```

C 跳过。

剩下继续压。

最后告诉你哪些文件没进去。

最近还刚修了 Windows 超过 260 字符路径导致的问题，这个是浏览器的锅，怎么不能支持路径超过260个字符的呢（小声蛐蛐Windows）。

这个工具现在看起来还是一个“ZIP 打包”。

但里面实际上基本都是各种边界情况。

# OCR 也从“识别一张图片”越写越歪了

OCR 最早确实只是想识别图片。

现在是 PaddleOCR + ONNX Runtime Web，在 Worker 里面直接跑。

有 Tiny、Small、Medium 不同模型。

图片扔进去：

```text
图片
↓
浏览器
↓
ONNX Runtime Web
↓
PaddleOCR
↓
文字 + 坐标
```

文件不用上传。

后来我又想：

既然图片能识别，PDF 为什么不行？

然后 PDF 又开始变复杂。

最蠢的实现当然是：

```text
PDF 100 页
↓
全部渲染成图片
↓
100 页全部 OCR
```

能跑。

就是纯属浪费算力。

因为很多 PDF 本身就是有文字层的。

所以现在流程是：

```text
PDF
↓
PDF.js
↓
读取这一页原生文字

文字够多
├─ 是 → 直接使用
│
└─ 否
   ↓
   渲染成图片
   ↓
   OCR
```

扫描书走 OCR。

正常电子 PDF 直接读文字。

两种 PDF 用同一个入口解决。

而且不是等 100 页全部结束以后才显示。

第一页面出来，你就可以先看第一页。

第二页好了就加第二页。

如果第 73 页炸了，前 72 页也不会跟着一起蒸发。

重新开始的时候，从没完成的位置继续。

这就是很多网页工具做到后面，我越来越在意的一点：

**不要只考虑“能不能跑”，还要考虑任务的各种边界情况和使用体验。**

# 人脸打码其实也是同一个思路

以前这种功能大部分网站都得上传图片。

但现在浏览器直接跑 MediaPipe 就行。

目前检测用的是 BlazeFace。

模型加载以后直接在浏览器检测人脸区域，再用 Canvas 做遮挡。

所以整个过程：

```text
本地图片
↓
本地检测
↓
本地 Canvas
↓
本地导出
```

没服务器什么事。

这也是我现在比较喜欢 Web 工具的地方。

很多以前必须有后端的功能，现在后端已经变成可选项了。

# 密码生成器我也不太想随便写

密码生成器算整个 Toolbox 里面最小的工具之一。

但这种东西反而不能乱写。

最明显的就是不能：

```js
Math.random()
```

然后告诉别人“这是随机密码”。

现在直接走 `crypto.getRandomValues()`。

随机索引还做了 rejection sampling，避免简单 `%` 带来的分布偏差。

Passphrase 还有英文和中文词表。

词表从 CDN 拉下来以后，会先做 SHA-256 校验。

确认文件没有变，再拿来生成。

同时会估算密码、PIN 和 Passphrase 的随机熵。

当然使用的过程中还发现有些转义字符会导致生成出来的密码有问题，所以又进行了处理。

当然它还是一个小工具。

# 快传则是另外一坨

文件传输这个功能现在实际上有两套完全不同的东西。

一个公网。

一个局域网。

公网快传必须经过服务器，因为两台设备可能根本不在一个网络里。

但是服务器可以只负责存密文。

所以现在大概是：

```text
文件
↓
浏览器 AES-GCM 加密
↓
加密后的分块
↓
EdgeOne Blob
↓
另一台设备下载密文
↓
浏览器解密
```

密码不会直接发到服务器。

原文件也不会以明文形式存在服务器。

而局域网就没必要这么绕。

局域网直接 WebRTC，当然还在进一步升级，现在beta也支持了更多的局域网传输协议，更快了。

Supabase 只负责设备之间互相找到对方，也就是 signaling。

真正的数据尽量设备直接传设备。

我没有强行把这两套东西统一成一个“优雅的传输架构”。

因为没有意义。

公网最重要的是能连上。

局域网最重要的是别绕服务器。

问题不一样，方案本来就应该不一样。

# 到版本控制器以后，这个 Toolbox 已经开始不像“小工具箱”了

Git / SVN 版本控制器则是另一个风格。

前面的东西至少还能算：

> 网页小工具。

版本控制器已经开始往完整工作台走了。

公开 GitHub 仓库可以直接通过 GitHub REST API 看。

本地 Git / SVN 则需要 Toolbox Agent。

里面有提交图、文件树、文件 Diff、版本对比这些东西。

但是目前有一个边界我故意：

**只读。**

不让网页随便：

```text
checkout
commit
reset
stage
```

SVN 也是受控调用 `svn.exe`，不是直接给网页一个 Shell。

可能未来会进一步升级成为不止读，更能改。

# Codex Session 是目前我觉得最有意思的一块

这个东西一开始只是为了：

> 我想看看 Codex 到底干了什么。

因为 Agent 跑一次任务以后，最终你可能只看到一句：

> Done.

但中间实际上发生了很多事情。

它执行了什么命令？

读了什么文件？

改了什么？

调用工具花了多久？

模型本身花了多久？

一共用了多少 Token？

哪个 Turn 特别贵？

有没有大量无意义的上下文？

所以现在 Codex Session 工具会直接读取 rollout JSONL，然后在本地解析。

里面可以看：

* 命令
* 文件
* Patch
* Tool
* Token
* Request
* Timeline
* Session 压缩

这里我有一个比较重要的原则：

**只分析证据，不猜。**

比如日志没有明确说一个工具成功了。

那就是 Unknown。

搜索结果里面出现了一个文件路径。

不代表 Agent 真的读过这个文件。

只有真正的 read 才算 read。

文件只有真正成功 patch 了，才算 changed。

Shell 命令也只是静态解析。

绝对不执行。

这个东西现在已经不能算普通“小工具”了。

更接近一个：

> AI Agent 调试器。

所以我现在感觉 Toolbox 后面很可能还会越来越往这种方向走。

不是单纯做：

```text
图片压缩
PDF 转文字
随机密码
```

而是慢慢变成一些真正的开发工作台。

未来这个也会逐渐支持opencode和claude code。

# 浏览器不是万能的，所以后来又有了 Toolbox Agent

做到 Git、本地大文件传输这些东西以后，浏览器权限开始明显不够用了。

浏览器安全模型决定了它不能随便：

* 扫你的硬盘
* 执行 Git
* 执行 SVN
* 开任意 TCP 服务
* 调系统接口
* 长期监听系统状态

以前我也考虑过：

那是不是干脆整个项目做成桌面软件？

Electron。

Tauri。

或者直接原生。

后来想想还是不对。

因为前面 80% 的功能明明浏览器自己就能跑。

为了剩下 20% 的功能，让所有用户下载一个客户端，感觉也挺蠢。

所以现在是：

```text
                Web
                 │
        ┌────────┴────────┐
        │                 │
普通浏览器用户        需要高级能力
                          │
                          ↓
                   Toolbox Agent
```

Agent 只是浏览器能力的补丁。

不是整个网站的运行基础。

我觉得这个边界目前还挺舒服。

没有安装 Agent，绝大部分工具照样能用。

装了以后，再解锁本地仓库、原生传输这些浏览器不方便干的东西。

# 后端现在也已经不是一个“后端”了

这个项目现在还有一个比较乱，但是我觉得挺实用的地方。

就是它没有一个统一的大后端。

不同事情扔给不同平台。

大概就是：

```text
2025-blog-public

├─ Netlify
│  └─ Next.js 站点
│
├─ Supabase
│  ├─ Likes
│  └─ WebRTC Signaling
│
├─ EdgeOne
│  └─ 公网加密文件中转
│
└─ Toolbox Agent
   └─ 本地原生能力
```

这肯定不是什么教科书式架构。

服务多。

配置也多。

有时候隔一阵子回来，我自己都得先翻架构文档。

但它有一个好处。

每个东西基本都能单独炸。

比如 EdgeOne 挂了。

公网快传挂。

博客不受影响。

Supabase 挂了。

点赞和局域网 signaling 有问题。

其他工具还能跑。

Agent 挂了。

纯网页功能继续用。

对于我这种一直往项目里面塞东西的人来说，这反而比一个巨型后端舒服。

# 这个项目最大的变化，其实是我对浏览器的看法变了

以前我觉得网页就是网页。

展示内容。

调 API。

顶多做一点简单计算。

但这个项目越写，我越觉得现代浏览器已经越来越像一个小型操作系统。

现在它已经可以：

```text
文件系统
Web Worker
WASM
WebCodecs
WebRTC
Web Crypto
Canvas
WebGL
ONNX Runtime
本地 AI 模型
流式读写
```

很多以前必须：

> 上传到服务器处理

的东西，现在已经不一定需要服务器。

所以 Toolbox 现在其实就是我不断测试浏览器边界的地方。

我经常会先问：

> 这个东西能不能纯浏览器做？

能。

那就纯浏览器。

不能。

再看缺的到底是什么。

缺网络，就上 Edge。

缺 Realtime signaling，就上 Supabase。

缺本地系统权限，就交给 Agent。

而不是一上来就：

> 搞个 Spring Boot 后端，然后又是进行接口调用，然后返回数据。

# 当然，现在还是一坨

说这么多并不代表这个项目现在架构有多漂亮。

完全没有。

目录越来越多。

依赖也越来越多。

有些模块一开始只是随手写，后面功能越长越大。

也推翻过不少方案。

比如文章页面做性能优化，改完以后发现实际效果不对，又直接 Revert。

点击效果也改了好几轮。

ZIP 这种看起来两天能写完的东西，后面一直在补各种奇怪边界，弄好了还需要做真实的测试。

Toolbox 现在也已经有点需要继续拆。

但我觉得这反而是这个项目比较真实的一点。
