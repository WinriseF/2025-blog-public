CDN 方案还有一个很容易做的“感知性能”优化 当前 zip.js 是到真正点击压缩后才： ```ts await loadZipRuntime() ``` 然后才： ```ts import( 'https://cdn.jsdelivr.net/npm/@zip.js/zip.js@2.8.59/index-native.min.js' ) ``` 这意味着： ```text 用户选择保存位置 ↓ 点击压缩 ↓ 等待 CDN ↓ 解析 JS ↓ 开始压缩 ``` 可以在目录扫描完成后立即后台预热： ```ts void preloadZipRuntime() ``` 变成： ```text 用户选择文件 ↓ 浏览文件树 / 配置压缩参数 │ └── 同时 CDN 下载 zip.js ↓ 点击压缩 ↓ 几乎立即开始 ``` 不改变 CDN 架构，也不会增加首屏 bundle。 这很适合你们现在的模式。 另外一个结论：`BlobReader(file)` 不需要改。 我专门核对了你们固定版本 `v2.8.59` 的 zip.js 实现。`BlobReader.createReadable()` 在读取完整 Blob/File 时本身直接调用： ```ts sourceBlob.stream() ``` 所以当前： ```ts new BlobReader(file) ``` 本质上已经走原生 `File/Blob.stream()`，不存在“先整个读进内存”的问题。 这部分保持不动即可。 还有一个你们已经选对的地方是默认 `智能打包 = level 6`。 zip.js 官方说明只有压缩等级 `6` 可以直接使用浏览器原生 `CompressionStream`；其他自定义等级比如 `9` 会切换到内置 Deflate 实现。([Gildas Lormeau][3]) 所以现在： ```text 智能打包 level 6 ``` 实际上就是性能非常好的默认路径。 而： ```text 最大压缩 level 9 ``` CPU 明显变高是正常现象，不需要优化成 9 默认。 我会按这个顺序改： | 优先级 | 修改 | 预期收益 | | --- | ---------------------------------- | ----------------- | | P0 | 排除规则只匹配目录 | 修真实逻辑错误 | | P0 | 默认排除目录不递归扫描，改 lazy | 极大改善大项目扫描 | | P1 | 扫描进度 100ms 节流 | 明显减少 React 开销 | | P1 | Checkbox 从 3 次 O(N) 降到 1 次 | 明显改善大树操作 | | P1 | 直接把 `createWritable()` 给 ZipWriter | 降低大 ZIP stream 开销 | | P1 | 提前 CDN preload | 降低点击压缩后的等待 | | P2 | 小文件 2~4 entry 并行 | 提高 CPU 利用率 | | P2
