# 软件体系结构中的 23 个 GoF 设计模式：从创建、组合到协作

---

软件体系结构关心的是系统如何拆分、依赖如何流动、边界如何保护、变化如何隔离。设计模式不是架构本身，但它会影响架构里的对象生命周期、模块边界、扩展点、协作方式和复杂度分布。


**TL;DR：** GoF 23 个设计模式来自《Design Patterns: Elements of Reusable Object-Oriented Software》，经典分类是创建型、结构型、行为型。创建型模式解决“对象由谁创建”，结构型模式解决“对象如何组合”，行为型模式解决“对象如何协作”。模式不是越多越好，真正有价值的模式使用，是把真实变化点压到清晰边界里。

---

## 1. 先把设计模式放回体系结构里

体系结构不是“用了多少模式”。一个项目里同时出现 Factory、Strategy、Observer、Proxy，并不说明架构好。架构好不好，取决于这些结构是否真的降低了变化成本。

可以用四个问题判断一个设计模式有没有架构价值：

| 问题 | 说明 |
|---|---|
| 变化点是否真实存在 | 没有真实变化点时，抽象会变成负担。 |
| 边界是否因此更清晰 | 模式应该让依赖方向更明确，而不是让调用链更绕。 |
| 复杂度是否被隔离 | 好的模式会把复杂度集中到少数稳定位置。 |
| 团队是否能一致理解 | 只有一个人懂的“高级设计”，长期维护风险很高。 |

GoF 原书把 23 个模式分成三类：

| 分类 | 核心问题 | 设计模式 |
|---|---|---|
| 创建型 | 对象怎么创建，创建细节放在哪里 | Abstract Factory、Builder、Factory Method、Prototype、Singleton |
| 结构型 | 类和对象如何组合，边界如何稳定 | Adapter、Bridge、Composite、Decorator、Facade、Flyweight、Proxy |
| 行为型 | 对象如何协作，流程如何扩展 | Chain of Responsibility、Command、Interpreter、Iterator、Mediator、Memento、Observer、State、Strategy、Template Method、Visitor |

这三个分类正好对应架构里的三个高频问题：

1. 生命周期问题：对象创建、缓存、复用、销毁由谁负责；
2. 边界问题：模块、外部系统、内部对象之间如何组合；
3. 协作问题：一次业务动作如何在多个对象之间传递、拆分和扩展。

## 2. 创建型模式：管理对象生命周期

创建型模式的重点不是“少写几个 new”，而是控制创建责任。

在小程序里，直接创建对象通常没有问题。在复杂系统里，对象创建经常伴随配置、依赖、资源、环境、租户、版本和策略。如果这些逻辑散落在业务代码中，后续改动会非常痛苦。

### 2.1 Abstract Factory：抽象工厂

**核心意图：** 创建一组相互匹配的对象，也就是一个产品族。

抽象工厂不只是创建某一个类，而是保证一整组对象来自同一个实现体系。例如支付系统里，支付宝实现应该同时提供支付客户端、退款客户端、回调验签器、账单下载器；微信支付实现也应该提供同一组能力。业务层不应该混用“支付宝支付客户端 + 微信验签器”。

适合场景：

| 场景 | 说明 |
|---|---|
| 多支付渠道 | 每个渠道都有支付、退款、验签、账单等一组对象。 |
| 多云厂商 | AWS、阿里云、腾讯云分别提供对象存储、队列、短信等实现。 |
| 多数据库方言 | MySQL、PostgreSQL、Oracle 有不同 SQL 生成器和分页器。 |
| 多主题 UI | 每套主题需要按钮、弹窗、表单、图标等组件保持风格一致。 |

架构价值：

1. 产品族一致性由工厂保证；
2. 业务代码依赖抽象，不依赖具体厂商；
3. 新增一套产品族时，修改点集中。

代价：

1. 新增产品族相对容易，新增产品类型会影响所有工厂；
2. 工厂接口太大时会变成“供应商能力清单”；
3. 如果不同产品族差异很大，强行统一接口会导致大量空实现。

一个支付场景的结构可以这样表达：

```ts
interface PaymentClient {
	pay(orderId: string, amount: number): Promise<string>
}

interface RefundClient {
	refund(paymentId: string, amount: number): Promise<void>
}

interface WebhookVerifier {
	verify(payload: string, signature: string): boolean
}

interface PaymentProviderFactory {
	createPaymentClient(): PaymentClient
	createRefundClient(): RefundClient
	createWebhookVerifier(): WebhookVerifier
}
```

这里的重点不是工厂方法本身，而是 `PaymentClient`、`RefundClient`、`WebhookVerifier` 被绑定到同一个 provider。

更完整地看，Abstract Factory 通常位于“业务用例层”和“基础设施实现层”之间。业务代码只知道自己需要一个支付能力集合，至于是微信、支付宝、Stripe，应该由配置、租户、地区或运行时上下文决定。这样做的好处是：渠道切换不会污染业务流程，测试时也可以直接换成内存实现或假实现。

落地时要特别注意工厂接口的颗粒度。如果一个工厂同时暴露几十个创建方法，说明它可能已经把多个边界混在一起了。更好的方式是按业务能力拆分工厂，例如支付工厂、消息工厂、存储工厂分别管理自己的产品族。抽象工厂不是“全局对象生产中心”，它应该代表一个清晰产品族。

判断是否需要 Abstract Factory，可以看三个信号：

1. 是否存在多套实现，而且每套实现内部的对象必须成组替换；
2. 调用方是否需要避免知道具体厂商、协议或部署环境；
3. 新增一套实现时，是否希望主要新增代码，而不是修改大量业务分支。

常见误用是只有一个产品类型时也上抽象工厂。比如系统只需要创建一个 `SmsClient`，没有同族对象，普通工厂函数或依赖注入已经足够。另一个误用是把工厂返回值做得过于通用，比如统一返回 `any` 或 `object`，这样反而丢掉类型约束，让错误延迟到运行时。

### 2.2 Builder：建造者

**核心意图：** 分步骤构造复杂对象，把构造过程和最终表示分开。

Builder 经常被误解成“链式调用”。链式调用只是表现形式，Builder 真正解决的是复杂对象构造时的可读性、校验和不变量维护。

适合场景：

| 场景 | 为什么适合 Builder |
|---|---|
| 查询条件 | 条件多、可选项多、组合关系复杂。 |
| HTTP 请求 | method、url、headers、body、timeout、retry 都可能配置。 |
| 报表任务 | 时间范围、维度、指标、过滤条件、导出格式需要组合。 |
| 工作流定义 | 节点、边、超时、重试、回调配置需要逐步构造。 |

好的 Builder 通常有三个特征：

1. 中间过程可以逐步设置；
2. `build()` 统一校验必填项和互斥项；
3. 最终对象最好是不可变的。

不好的 Builder 只是把构造函数参数搬到一堆 setter 里，既没有校验，也没有减少复杂度。

Builder 的架构价值在于把“对象构造协议”显式化。复杂对象往往不是所有字段随便组合都合法，比如报表任务必须有时间范围，导出格式决定了可选参数，某些指标只能用于某些维度。如果这些规则散落在调用方，系统会出现很多半合法对象。把规则集中到 `build()`，可以让非法状态尽早失败。

一个成熟 Builder 通常会处理这些事情：

1. 必填字段检查，例如没有 `url` 就不能创建 HTTP 请求；
2. 互斥字段检查，例如 `jsonBody` 和 `formBody` 不能同时存在；
3. 默认值填充，例如超时时间、重试次数、分页大小；
4. 派生字段计算，例如根据维度自动生成查询分组；
5. 最终对象冻结，避免构造完成后被随意修改。

需要区分 Builder 和参数对象。参数对象适合字段虽然多但规则简单的场景；Builder 适合构造过程本身有步骤、有约束、有默认策略的场景。如果只是为了避免构造函数参数太长，直接使用具名配置对象可能更清楚。

Builder 的另一个风险是让对象变得过度灵活。一个 Builder 如果允许调用方设置所有内部字段，实际就是暴露了对象内部结构。更好的设计是只暴露业务上有意义的构造步骤，把内部派生字段、缓存字段、运行时资源留在对象内部处理。

### 2.3 Factory Method：工厂方法

**核心意图：** 定义创建对象的接口，把具体创建逻辑交给子类、插件或扩展点。

Factory Method 和 Abstract Factory 很像，但粒度更小。Factory Method 通常只创建一种产品；Abstract Factory 创建一组相关产品。

它在框架设计里非常常见：框架定义主流程，业务方只需要实现某个创建点。例如任务调度框架提供 `createJobHandler()`，不同业务返回自己的任务处理器；导入框架提供 `createParser()`，不同文件类型返回不同解析器。

适合场景：

1. 框架需要把对象创建权交给扩展方；
2. 父类或模板流程不知道具体产品类型；
3. 具体实现依赖运行时配置、插件、租户或上下文。

需要注意的是，现代工程里不一定要用继承式 Factory Method。很多时候，注册表、依赖注入容器、函数映射表更直接。

```ts
type Parser = {
	parse(input: string): unknown
}

const parserRegistry = new Map<string, () => Parser>()

parserRegistry.set('json', () => ({
	parse: input => JSON.parse(input)
}))

function createParser(type: string): Parser {
	const factory = parserRegistry.get(type)
	if (!factory) {
		throw new Error(`Unsupported parser type: ${type}`)
	}
	return factory()
}
```

这段代码没有继承层级，但保留了 Factory Method 的核心思想：调用方不直接依赖具体解析器。

Factory Method 在框架中的核心作用，是把“稳定流程”和“变化实现”分开。框架负责调度生命周期，例如加载配置、打开文件、记录日志、捕获异常；扩展方只负责提供某个具体对象，例如解析器、处理器、验证器。这样框架不用知道所有业务类型，业务也不用重写主流程。

在现代应用里，它经常以三种形态出现：

1. 继承式：父类定义 `createParser()`，子类返回具体解析器；
2. 注册式：启动时把 `type -> factory` 放进注册表；
3. 容器式：依赖注入容器根据名称、类型或注解提供实现。

三种形态没有绝对优劣。继承式适合框架骨架稳定、扩展点少的场景；注册式适合插件系统和运行时扩展；容器式适合业务服务很多、生命周期由框架统一管理的后端应用。关键是调用方不直接写 `new JsonParser()`，而是通过稳定创建点拿到对象。

误用 Factory Method 的典型表现，是为了创建一个简单对象引入一套继承结构。比如只是在两个地方 `new User()`，没有扩展点，也没有运行时选择，就不需要工厂方法。模式应该服务于变化，而不是把对象创建变成仪式。

### 2.4 Prototype：原型

**核心意图：** 通过复制已有对象来创建新对象。

Prototype 适合对象初始化成本高、结构复杂、需要从模板派生的场景。

常见例子：

| 场景 | 说明 |
|---|---|
| 工作流模板 | 从模板复制出具体流程实例。 |
| 文档模板 | 从合同模板、审批模板、报告模板创建新文档。 |
| 游戏对象 | 从预制对象复制出大量实例。 |
| 规则配置 | 从默认规则派生租户级配置。 |

Prototype 的关键风险是复制语义。

浅拷贝会共享内部引用。如果复制出来的对象修改了数组、Map、嵌套配置，可能影响原型对象。深拷贝可以降低共享风险，但成本更高，也可能复制不该复制的资源，比如数据库连接、文件句柄、缓存引用、事件订阅。

所以 Prototype 在架构设计里必须回答三个问题：

1. 哪些字段属于可复制状态；
2. 哪些字段必须重新生成；
3. 复制后对象和原型之间是否仍有关系。

在业务系统里，Prototype 最常出现在“模板 -> 实例”的转换中。审批流程模板会复制出某一次具体审批，问卷模板会复制出某一次投放，报表模板会复制出某个租户的定制报表。这类场景的重点不是复制技术，而是复制边界：模板里的节点、规则、默认配置可以复制，但运行记录、审批人当前状态、执行日志不能复制。

一个安全的 Prototype 设计通常会显式定义复制方法，而不是完全依赖通用深拷贝：

1. `cloneAsDraft()`：复制为草稿，重置发布状态；
2. `cloneForTenant(tenantId)`：复制给某个租户，替换租户上下文；
3. `cloneWithNewIdentity()`：复制结构但重新生成 ID；
4. `snapshot()`：只复制可审计状态，不复制运行时依赖。

这样做比 `JSON.parse(JSON.stringify(obj))` 更可靠。通用深拷贝看起来方便，但会丢失日期、方法、循环引用、Map、Set，也容易把不该复制的资源一起复制。架构上，复制语义应该是领域语义，而不是序列化技巧。

Prototype 还要考虑版本问题。模板升级后，已经复制出去的实例是否跟着升级？如果不升级，系统要能同时运行多个版本；如果升级，就要定义迁移规则。这一点在工作流、表单、规则引擎里非常关键。

### 2.5 Singleton：单例

**核心意图：** 保证一个类只有一个实例，并提供全局访问点。

Singleton 是最容易滥用的模式之一。它看起来能解决“全局只有一个”的问题，但经常引入隐藏依赖和全局状态。

适合谨慎使用的场景：

1. 进程级配置快照；
2. 日志门面；
3. 指标注册器；
4. 连接池管理器；
5. 本地缓存管理器。

但在现代后端系统里，更推荐把“单例生命周期”交给依赖注入容器，而不是在类内部写静态实例。比如 Spring 的 `FactoryBean` 文档明确区分了 singleton 和 prototype 两种对象管理方式，这说明对象生命周期应该是一种容器级能力，而不一定要由业务类自己控制。

Singleton 的主要问题：

| 问题 | 影响 |
|---|---|
| 隐藏依赖 | 调用方看不出真实依赖，测试替换困难。 |
| 全局状态 | 多测试用例、并发请求、不同租户之间容易互相污染。 |
| 初始化顺序 | 复杂系统里容易出现启动时序问题。 |
| 生命周期僵硬 | 想要释放、重建、热更新都更麻烦。 |

判断一个 Singleton 是否合理，可以问：如果明天要为不同租户提供不同实例，这个设计会不会崩？如果会，就应该考虑依赖注入、工厂或上下文容器。

单例真正的问题不是“只有一个实例”，而是“谁有权决定只有一个”。如果是进程级资源，例如日志门面、指标注册器、连接池管理器，由容器或运行时统一管理通常没有问题。如果业务类自己持有静态实例，它就把生命周期、依赖、初始化顺序和测试替换都锁死了。

在后端系统里，很多看似适合单例的对象其实只适合“容器单例”。例如 `OrderService` 在 Spring 里默认是 singleton scope，但它不是 GoF 意义上的 Singleton：它没有私有构造函数，也没有全局静态访问点，测试时可以替换，容器销毁时也能释放。这种差异很重要。

使用 Singleton 前应该确认：

1. 它是否无状态，或只持有线程安全状态；
2. 它是否不依赖请求、用户、租户、地区这些上下文；
3. 它是否支持测试替换和资源释放；
4. 它是否不会因为全局缓存导致数据串扰；
5. 它是否不需要热更新或多版本并存。

如果这些问题答不上来，优先选择依赖注入、工厂、上下文对象或显式生命周期管理。单例可以存在，但应该被框架管理，而不是成为到处可访问的全局变量。

## 3. 结构型模式：管理对象组合和模块边界

结构型模式解决的是“如何把对象组合成更大的结构”。从体系结构看，它们经常出现在模块边界、第三方集成、复杂对象树、横切能力和资源优化里。

### 3.1 Adapter：适配器

**核心意图：** 把一个接口转换成调用方期望的另一个接口。

Adapter 在架构中最重要的作用是保护边界。尤其是对接第三方系统时，外部 SDK 的模型、异常、状态码、分页方式、重试语义都不应该直接进入核心业务层。

典型场景：

1. 支付渠道 SDK 适配成统一 `PaymentGateway`；
2. 对象存储厂商适配成统一 `ObjectStorage`；
3. 老系统接口适配成新系统内部命令；
4. 外部用户模型适配成内部领域模型。

Adapter 的好处不是“把名字改一改”，而是把外部变化隔离在边界层。

```ts
type InternalUser = {
	id: string
	displayName: string
	email: string
}

type VendorUser = {
	user_id: string
	nickname: string
	mail_address: string
}

function adaptVendorUser(user: VendorUser): InternalUser {
	return {
		id: user.user_id,
		displayName: user.nickname,
		email: user.mail_address
	}
}
```

如果内部系统到处都在使用 `VendorUser`，说明边界已经泄漏。

Adapter 的关键不是“转换字段名”，而是翻译边界语义。外部系统的分页可能是 `page + size`，内部系统可能使用游标；外部错误码可能只有字符串，内部需要区分可重试、不可重试、权限失败；外部金额可能用浮点数，内部必须用最小货币单位。Adapter 应该把这些差异在边界处消化掉。

一个好的 Adapter 通常包含三类转换：

1. 数据结构转换：字段名、类型、枚举值、单位；
2. 协议语义转换：分页、排序、幂等、重试、超时；
3. 错误模型转换：外部异常变成内部可处理的错误类型。

如果 Adapter 只做字段搬运，调用方仍然需要理解外部系统的状态码、分页规则和异常，那边界没有真正被保护。尤其在对接支付、物流、短信、云厂商时，Adapter 层应该是外部不稳定性的缓冲区。

Adapter 也不要变成业务规则中心。它负责把外部世界翻译成内部语言，不应该决定订单是否能发货、用户是否能退款这类核心规则。业务规则应该留在领域层或应用服务层，否则外部系统一变，核心业务也会跟着晃。

### 3.2 Bridge：桥接

**核心意图：** 将抽象部分和实现部分分离，使它们可以独立变化。

Bridge 适合两个维度都会变化的场景。如果不用 Bridge，系统往往会出现类爆炸。

例如通知系统有两个变化维度：

1. 通知类型：订单通知、告警通知、营销通知；
2. 发送通道：邮件、短信、站内信、Webhook。

如果用继承组合，可能会出现 `OrderEmailNotification`、`OrderSmsNotification`、`AlertEmailNotification`、`AlertSmsNotification` 等大量类。Bridge 会把“通知抽象”和“发送实现”拆开。

适合场景：

| 抽象维度 | 实现维度 |
|---|---|
| 报表类型 | PDF、Excel、CSV、HTML |
| 消息类型 | 邮件、短信、Webhook、站内信 |
| 图形形状 | Canvas、OpenGL、终端字符、浏览器绘图 |
| 存储服务 | 本地文件、S3、OSS、MinIO |

Bridge 的代价是对象关系变多。只有当两个维度确实都在变化时，它才值得引入。

Bridge 的核心判断是“变化维度是否独立”。如果通知类型经常变化，发送渠道也经常变化，而且二者可以任意组合，那么 Bridge 很合适。通知对象负责业务语义，例如订单通知、告警通知；发送实现负责技术通道，例如邮件、短信、Webhook。两边通过接口连接，而不是通过继承笛卡尔积膨胀。

它和 Strategy 很像，但关注点不同。Strategy 通常是在一个上下文里替换算法；Bridge 是把一个抽象拆成两个可独立演进的层次。比如“报表”与“导出格式”之间是 Bridge，因为报表类型和格式类型都可能扩展；“选择哪种排序算法”更像 Strategy，因为主要变化点是算法本身。

使用 Bridge 时，要让抽象侧表达业务意图，实现侧表达技术能力。不要把所有方法都塞到实现接口里，否则实现侧会被业务概念污染。比如 `MessageSender` 可以有 `send(message)`，但不应该有 `sendOrderPaidMessage()`、`sendMarketingCouponMessage()` 这类业务方法。

Bridge 的误用通常出现在只有一个维度变化时。如果只有发送渠道变化，通知类型固定，普通 Strategy 或 Adapter 已经足够。过早 Bridge 会让代码多出两套接口和组合关系，读者需要绕一圈才能看懂真实调用。

### 3.3 Composite：组合

**核心意图：** 让调用方用统一接口处理单个对象和组合对象。

Composite 适合树形结构。

常见场景：

1. 文件和目录；
2. 菜单和子菜单；
3. 组织架构；
4. 权限树；
5. 页面组件树；
6. 表达式树；
7. 规则树。

Composite 的架构价值在于：调用方不必关心当前对象是叶子节点还是容器节点。

```ts
interface PermissionNode {
	getCode(): string
	contains(code: string): boolean
}

class Permission implements PermissionNode {
	constructor(private readonly code: string) {}

	getCode() {
		return this.code
	}

	contains(code: string) {
		return this.code === code
	}
}

class PermissionGroup implements PermissionNode {
	constructor(
		private readonly code: string,
		private readonly children: PermissionNode[]
	) {}

	getCode() {
		return this.code
	}

	contains(code: string) {
		return this.code === code || this.children.some(child => child.contains(code))
	}
}
```

需要注意：

1. 树可能很深，递归要考虑栈和性能；
2. 树可能出现循环，尤其是组织关系、依赖关系、标签关系；
3. 子节点和父节点的生命周期要明确；
4. 大树遍历要考虑缓存、分页和权限过滤。

Composite 的价值在于统一“单个对象”和“对象集合”的使用方式。调用方不需要写两套逻辑分别处理文件和目录、菜单项和菜单组、权限点和权限组。对调用方来说，它只面对一个 `Node` 接口，递归结构被封装在对象内部。

但 Composite 一定要明确树的所有权。父节点删除时是否删除子节点？子节点能否同时属于多个父节点？移动节点时是否保留历史路径？这些问题如果不先定义，后续会在权限、缓存、审计、搜索索引里产生连锁问题。

在大型系统里，Composite 还会遇到性能问题。权限树、组织树、商品类目树可能有几万甚至几十万个节点，不能每次请求都递归全量遍历。常见优化包括：

1. 为路径维护 materialized path；
2. 为父子关系维护闭包表；
3. 对热点子树做缓存；
4. 遍历时限制深度和返回字段；
5. 对树结构变更做异步索引更新。

Composite 不适合所有层级关系。如果关系本质是图，例如标签依赖、模块依赖、社交关系，强行当树处理会掩盖多父节点和环的问题。这个时候需要图模型、拓扑排序或显式依赖分析，而不是 Composite。

### 3.4 Decorator：装饰器

**核心意图：** 在不改变对象接口的前提下，动态叠加行为。

Decorator 和继承都能扩展行为，但 Decorator 更适合横向能力叠加。例如一个 HTTP 客户端可以被依次包装为：带日志的客户端、带重试的客户端、带指标的客户端、带缓存的客户端。

Java 标准库里的 `FilterInputStream` 就是典型例子：它包装另一个输入流，并在读取过程中增加额外行为或转换。

架构中常见装饰能力：

| 能力 | 示例 |
|---|---|
| 日志 | 记录请求参数、响应时间、错误信息。 |
| 指标 | 上报耗时、成功率、吞吐量。 |
| 缓存 | 对只读请求增加缓存层。 |
| 重试 | 对短暂失败做有限重试。 |
| 限流 | 在调用外部服务前做流量控制。 |
| 鉴权 | 在执行前验证身份和权限。 |

Decorator 最大的风险是顺序敏感。

例如缓存放在鉴权之前，可能导致未授权用户拿到缓存结果；重试包在事务外和包在事务内，语义也完全不同。使用 Decorator 时，必须明确装饰顺序。

Decorator 适合横切能力，因为它不需要修改被包装对象。一个基础 `HttpClient` 可以被包装成带超时、带重试、带熔断、带指标的客户端。每一层只关心自己的职责，最终组合出完整能力。

组合顺序是 Decorator 的核心设计点。以远程调用为例，常见顺序可能是：鉴权 -> 限流 -> 熔断 -> 重试 -> 超时 -> 指标 -> 实际调用。顺序不同，语义就不同。重试放在限流之前会放大流量，缓存放在鉴权之前会产生安全问题，指标放在重试内外统计口径也不同。

Decorator 和 Proxy 的区别在于意图。Decorator 主要是增加行为，调用方通常仍然认为自己在使用同一个能力；Proxy 主要是控制访问，可能隐藏远程、权限、懒加载等访问机制。在真实代码里两者会重叠，但设计讨论时要分清你是在扩展行为，还是在控制访问。

Decorator 的误用是包装层过多却没有可观测性。调用栈里套了十层对象，线上出问题时不知道请求在哪一层被拦截、改写或吞掉。生产代码里最好给关键装饰层加清晰命名、日志和指标，必要时在启动时打印最终组合链路。

### 3.5 Facade：外观

**核心意图：** 为复杂子系统提供一个简单入口。

Facade 在架构分层里很常见。比如订单模块内部可能涉及库存、优惠、支付、履约、发票、通知，但对外只暴露 `OrderFacade.placeOrder()`。

Facade 的价值：

1. 降低调用方认知成本；
2. 隐藏子系统内部协作；
3. 稳定跨模块 API；
4. 减少外部对内部细节的依赖。

但 Facade 很容易变成“万能服务”。如果所有业务流程都进入同一个 Facade，最后它会变成新的中心化泥球。

好的 Facade 应该代表一个清晰的业务边界，而不是一个“什么都能调”的工具类。

Facade 在分层架构里经常对应应用服务入口。它把多个领域对象、仓储、外部服务和事务边界编排在一起，对外提供一个稳定用例。例如 `OrderFacade.placeOrder()` 可以内部完成库存校验、价格计算、优惠锁定、订单创建、支付单生成，但调用方不需要知道这些步骤。

一个好的 Facade 有两个特征：第一，它面向用例，而不是面向数据库表；第二，它隐藏协作，但不隐藏业务结果。调用方应该能从返回值和异常类型里理解业务结果，例如下单成功、库存不足、优惠失效，而不是只拿到一个模糊的 `false`。

Facade 的边界也需要治理。如果它暴露太多细粒度方法，例如 `queryInventory()`、`lockCoupon()`、`createPayment()`，调用方仍然在自己编排流程，Facade 只是换了名字。如果它暴露太多不相关用例，又会变成万能服务。更好的做法是按业务能力拆成多个 Facade，例如订单、支付、履约、售后各自有入口。

Facade 不应该成为绕过领域模型的捷径。如果所有规则都堆在 Facade 里，领域对象只剩数据结构，系统会退化成过程式脚本。Facade 负责用例编排，核心不变量仍然应该由领域对象、策略、规则或状态机维护。

### 3.6 Flyweight：享元

**核心意图：** 共享大量细粒度对象的内部状态，降低内存占用。

Flyweight 适合对象数量巨大、重复状态很多的场景。

例子：

1. 文本编辑器里的字符样式；
2. 地图系统里的图标样式；
3. 游戏里的贴图、材质、模型；
4. 商品系统里的规格模板；
5. 权限系统里的权限元数据。

Flyweight 的核心是区分内部状态和外部状态：

| 状态类型 | 含义 | 是否共享 |
|---|---|---|
| 内部状态 | 稳定、可复用、与上下文无关 | 可以共享 |
| 外部状态 | 与上下文有关，例如位置、用户、数量、时间 | 不能共享 |

错误使用 Flyweight 的常见问题，是把本该属于上下文的状态放进共享对象，最后导致不同请求、不同用户、不同租户之间串数据。

Flyweight 的关键是把对象状态拆成内部状态和外部状态。内部状态可以共享，例如字体名称、图标资源、商品规格模板；外部状态必须由调用方传入，例如字符位置、图标坐标、当前用户、购买数量。共享对象越稳定，Flyweight 越安全。

它通常需要一个工厂或缓存来管理共享实例。例如同一个字体样式只创建一次，后续通过 key 复用。这个 key 必须足够准确：如果字体大小、字重、颜色都会影响渲染，它们都应该进入 key。key 太粗会串状态，key 太细会失去复用价值。

Flyweight 更适合高频、大量、重复的对象。如果系统只有几十个对象，引入共享池没有意义。它真正有价值的地方，是文本编辑器字符渲染、地图 POI 图标、游戏资源、权限元数据这类对象数量大且重复度高的场景。

还要注意并发和淘汰策略。共享对象如果可变，就要考虑线程安全；缓存如果无限增长，就会从优化变成内存泄漏。生产实现通常会配合只读对象、弱引用、LRU、引用计数或资源生命周期管理。

### 3.7 Proxy：代理

**核心意图：** 用代理对象控制对真实对象的访问。

Proxy 在现代架构里无处不在：RPC 客户端、ORM 懒加载、AOP、事务代理、缓存代理、权限代理、远程服务代理都属于这个思路。

Java 的 `java.lang.reflect.Proxy` 官方文档说明，运行时可以创建实现指定接口的代理类，并把方法调用派发给 invocation handler。这正是很多框架实现动态代理的基础。

常见代理类型：

| 类型 | 作用 |
|---|---|
| 远程代理 | 把远程服务调用伪装成本地接口调用。 |
| 虚拟代理 | 对昂贵对象做懒加载。 |
| 保护代理 | 在访问真实对象前做权限控制。 |
| 缓存代理 | 对结果进行缓存。 |
| 监控代理 | 记录耗时、错误、调用次数。 |

Proxy 的最大风险是隐藏成本。代码看起来像普通方法调用，但背后可能跨网络、访问数据库、开启事务、触发懒加载或重试。

所以使用代理时，接口命名、超时配置、错误语义和可观测性必须清楚。

Proxy 的架构价值在于把访问控制集中到边界上。远程服务客户端可以通过代理统一处理超时、重试、熔断、鉴权、日志；数据库实体可以通过代理实现懒加载；权限系统可以通过代理拦截敏感操作。调用方使用的是同一个接口，但访问路径被代理接管。

也正因为代理会隐藏访问路径，它必须把隐藏成本重新暴露到工程约束里。远程代理的方法命名最好能暗示远程调用，例如 `paymentClient.charge()` 比 `payment.charge()` 更清楚；懒加载代理要避免在循环里触发 N+1 查询；事务代理要明确哪些方法会开启事务，哪些不会。

Proxy 和 Adapter 的边界也常被混淆。Adapter 解决接口不兼容，重点是转换；Proxy 解决访问控制，重点是拦截。比如把第三方短信 SDK 包装成内部 `SmsClient` 是 Adapter；给 `SmsClient` 加重试、限流、审计是 Proxy 或 Decorator。

生产系统里的代理最好配套观测能力。动态代理、AOP、ORM 懒加载都可能让调用链变得不透明。日志、trace、metrics、超时配置和错误分类，是代理从“方便”变成“可靠”的必要条件。

## 4. 行为型模式：管理对象协作和流程扩展

行为型模式关注的是对象之间如何通信、请求如何流动、算法如何替换、状态如何迁移。

从体系结构看，行为型模式最容易影响业务流程的可读性。用得好，流程可插拔、可扩展；用得差，调用链断裂，调试困难。

### 4.1 Chain of Responsibility：责任链

**核心意图：** 让多个处理器都有机会处理请求，请求沿链路传递。

责任链在 Web 框架和业务规则系统里非常常见。

常见场景：

1. HTTP middleware；
2. Servlet filter；
3. 网关鉴权、限流、日志、路由；
4. 审批流；
5. 风控规则；
6. 异常处理链。

责任链适合“多个步骤按顺序处理同一个上下文”的场景。

```ts
type RequestContext = {
	userId?: string
	token?: string
	blocked?: boolean
}

type Handler = {
	handle(ctx: RequestContext, next: () => Promise<void>): Promise<void>
}

const authHandler: Handler = {
	async handle(ctx, next) {
		if (!ctx.token) {
			ctx.blocked = true
			return
		}
		await next()
	}
}
```

责任链的风险：

1. 链路顺序影响结果；
2. 上下文被多个 handler 修改后，状态来源不清楚；
3. 某个 handler 中断链路时，后续逻辑不会执行；
4. 异步链路里的错误处理容易混乱。

所以责任链要有清晰的执行约定：能否短路、能否修改上下文、错误如何传播、是否允许重复执行。

责任链的设计重点是链路协议。每个处理器到底是必须调用 `next()`，还是可以短路？能否修改上下文？异常是向外抛出，还是写入结果对象？这些规则比处理器类本身更重要。协议不清楚时，链路会变成隐式控制流，调试非常困难。

在 Web 中间件里，责任链通常处理横切流程：认证、限流、日志、路由、异常处理。业务规则系统里，它可以处理风控规则、审批条件、优惠规则。两类场景的差异是：中间件链路通常强调顺序，规则链路可能强调命中策略，例如全部通过、任一通过、按优先级短路。

责任链适合处理“同一个上下文按步骤流动”。如果每个处理器处理的是完全不同的数据结构，或者后续步骤强依赖前面步骤的私有实现，就不适合简单责任链，可能更像工作流、状态机或 pipeline。

常见误用是把复杂业务流程拆成一串看似松耦合的 handler，但每个 handler 都偷偷读写同一个大上下文。结果是字段来源不清楚，顺序一改就坏。更健康的做法是限制上下文字段、给关键状态建模，并为每个 handler 明确输入输出。

### 4.2 Command：命令

**核心意图：** 把一次请求封装成对象。

Command 是架构里非常实用的模式。它让“请求的发起”和“请求的执行”分离。

适合场景：

| 场景 | 为什么适合 Command |
|---|---|
| 消息队列 | 消息本身就是延迟执行的命令。 |
| 任务调度 | 任务参数、执行器、重试策略可以封装在命令里。 |
| 撤销重做 | 每个操作都可以记录并反向执行。 |
| 审计日志 | 命令对象天然记录谁在什么时候做了什么。 |
| 工作流 | 每个节点可以是一个命令。 |

一个生产级 Command 通常不只是 `execute()`，还需要：

1. 命令 ID；
2. 发起人；
3. 幂等键；
4. 参数版本；
5. 重试策略；
6. 超时时间；
7. 审计信息。

Command 的主要代价是版本治理。只要命令被持久化到数据库、消息队列或日志系统，就要考虑旧命令在新代码里能否继续执行。

Command 的真正价值是把“想做什么”变成一个可以传递、排队、记录和重放的对象。一次退款、一封邮件、一个报表导出任务、一次库存补偿，都可以表示成命令。系统可以立即执行，也可以放到队列里延迟执行，还可以在失败后重试。

一个可靠命令对象通常不只包含业务参数，还包含执行语义：

1. `commandId` 用于追踪；
2. `idempotencyKey` 用于防重复；
3. `requestedBy` 用于审计；
4. `schemaVersion` 用于兼容；
5. `executeAfter` 用于延迟；
6. `retryPolicy` 用于失败处理。

Command 与事件也要区分。命令表示“请求系统做一件事”，通常有意图、有目标、有发起人；事件表示“某件事已经发生”，通常用于通知和订阅。`RefundPaymentCommand` 是命令，`PaymentRefundedEvent` 是事件。混用二者会让流程语义混乱。

误用 Command 的典型问题是命令过于贫血，只是把函数参数包了一层对象，没有带来排队、审计、撤销、重试或解耦价值。另一个问题是命令执行器里直接依赖当前代码结构，导致历史命令在版本升级后无法重放。只要命令持久化，就必须把它当作长期契约。

### 4.3 Interpreter：解释器

**核心意图：** 为语言定义语法表示，并解释执行。

Interpreter 适合小型 DSL，而不是通用编程语言。

常见场景：

1. 规则表达式；
2. 权限表达式；
3. 查询条件表达式；
4. 模板表达式；
5. 简单公式引擎。

例如权限表达式：

```text
role == "admin" or department == "finance"
```

如果表达式语法很小，Interpreter 可以很清晰。但如果需求持续扩张，出现变量、函数、循环、异常、模块、调试器、安全沙箱，就说明你已经在做一门语言了。这个时候应该考虑成熟表达式引擎、规则引擎或脚本语言，而不是继续手写解释器。

Interpreter 的架构风险：

1. 语法扩展失控；
2. 表达式安全问题；
3. 性能不可控；
4. 错误提示难写；
5. 调试体验差。

Interpreter 的适用范围通常比很多人想象得窄。它适合表达式规模小、语法稳定、执行环境可控的领域语言，例如优惠规则、权限判断、过滤条件、简单公式。它不适合承载完整业务流程，也不适合替代一门通用脚本语言。

一个小型 Interpreter 一般包含四层：

1. 词法分析，把字符串拆成 token；
2. 语法分析，把 token 转成 AST；
3. 语义检查，确认字段、函数、类型是否合法；
4. 执行器，在受控上下文里解释 AST。

很多项目一开始只写第四层，直接用字符串切割和 `if` 判断解释表达式。短期能跑，长期会在优先级、括号、错误提示、安全和扩展上吃亏。只要表达式会给用户配置，就应该认真处理语法和错误信息。

安全是 Interpreter 的底线。表达式不能随意访问系统对象，不能执行任意代码，不能无限循环，也不能构造高复杂度表达式拖垮系统。成熟做法包括白名单函数、执行超时、AST 节点数限制、字段权限检查和表达式预编译缓存。

### 4.4 Iterator：迭代器

**核心意图：** 在不暴露集合内部结构的情况下，顺序访问元素。

Iterator 不只是数组遍历。在系统架构里，它还对应分页、游标、流式读取和批处理。

常见场景：

1. 内存集合；
2. 数据库游标；
3. 分页 API；
4. 消息流；
5. 大文件逐行读取；
6. 批量导出。

架构里使用 Iterator 时，最容易忽略四个问题：

| 问题 | 说明 |
|---|---|
| 资源释放 | 数据库游标、文件句柄、网络连接需要关闭。 |
| 一致性 | 分页期间数据变化，可能重复或漏读。 |
| 背压 | 消费速度低于生产速度时，要控制读取节奏。 |
| 错误恢复 | 迭代中途失败后，能否从断点继续。 |

所以大规模数据迭代不能只套一个 `for...of` 思维。它需要 checkpoint、分页 token、超时、重试和资源清理策略。

Iterator 的架构意义是把“如何取下一批数据”隐藏起来。调用方只关心是否还有下一项，不需要知道底层是数组、数据库游标、分页 API、Kafka 分区还是对象存储文件列表。这样一来，数据源可以变化，消费逻辑相对稳定。

但工程里的 Iterator 很少只是内存遍历。跨网络或跨数据库的迭代必须处理一致性和资源生命周期。例如分页 API 在迭代过程中有新数据插入，可能导致重复或漏读；数据库游标长时间打开，会占用连接；消息流消费失败，需要提交或回滚 offset。

设计 Iterator 时要明确这些问题：

1. 迭代顺序是否稳定；
2. 是否支持从断点恢复；
3. 每批大小如何控制；
4. 失败后是否会重复消费；
5. 调用方是否需要显式关闭资源；
6. 是否需要背压或速率限制。

Iterator 和批处理经常一起出现。一个好的批处理接口不应该一次把所有数据读进内存，而应该提供流式或分页迭代能力，并让调用方可以在每一批之间提交进度。这样系统才能处理大数据量，而不是只在测试数据下正常。

### 4.5 Mediator：中介者

**核心意图：** 用一个中介对象封装多个对象之间的交互。

当多个对象互相调用，形成网状依赖时，Mediator 可以把协作逻辑集中起来。

适合场景：

1. UI 表单联动；
2. 多个组件之间的状态同步；
3. 工作流编排；
4. 领域服务协调多个聚合；
5. 聊天室消息分发。

Mediator 的好处是降低对象之间的直接耦合。组件不需要知道彼此，只需要告诉中介者发生了什么。

风险也很明显：中介者可能变成上帝对象。

判断一个 Mediator 是否健康，可以看它是否表达一个明确流程。如果它只是因为“不知道逻辑放哪”而承接所有业务规则，那它很快会变成难以维护的中心类。

Mediator 适合管理多对象协作，但它不应该替代对象本身的职责。比如表单页面里，国家、城市、邮编、配送方式几个控件互相影响，把联动逻辑放到表单中介者里是合理的；但每个控件自己的校验和展示状态仍应该留在控件内部。

在领域模型中，Mediator 常以应用服务、流程编排器、Saga 协调器的形态出现。它负责调用多个聚合或外部服务，保证流程顺序和补偿逻辑。例如创建订单可能涉及购物车、库存、优惠、支付、通知，这些对象不应该互相直接调用，而应该由一个用例协调者编排。

健康的 Mediator 有清晰边界：

1. 它表达一个用例或一个协作场景；
2. 它不保存过多长期状态；
3. 它不吞掉所有领域规则；
4. 它的输入输出可以被测试；
5. 它不会让所有模块都依赖它。

一旦 Mediator 变成“所有对象都找它”的中心，系统依赖会反向集中，修改任何业务都要碰它。这时需要拆分按用例的协调器，把规则下沉到合适的领域对象或策略里。

### 4.6 Memento：备忘录

**核心意图：** 在不暴露对象内部结构的情况下，保存和恢复对象状态。

Memento 常用于撤销、回滚、快照和检查点。

典型场景：

1. 编辑器撤销重做；
2. 流程执行检查点；
3. 仿真系统回滚；
4. 表单草稿；
5. 事务补偿前状态；
6. 游戏存档。

Memento 的设计重点是状态保存策略。

| 策略 | 优点 | 代价 |
|---|---|---|
| 完整快照 | 恢复简单 | 存储成本高，敏感数据风险高。 |
| 差量快照 | 节省空间 | 恢复链路复杂。 |
| 事件日志 | 可审计、可重放 | 需要保证事件版本兼容。 |
| 可重建指针 | 存储最少 | 依赖外部数据仍可用。 |

真实系统里，Memento 往往和审计、合规、隐私、安全相关。保存快照前必须明确：哪些字段不能保存，保存多久，谁能读取，如何删除。

Memento 的关键是“恢复能力”。编辑器撤销需要恢复文档状态，流程引擎需要从检查点继续执行，配置中心需要回滚到历史版本。它保存的不是任意备份，而是一个对象在特定时刻可恢复的状态。

实现 Memento 时，要先选择快照粒度。完整快照简单但成本高，差量快照节省空间但恢复复杂，事件日志可追溯但需要重放能力。不同场景选择不同策略：文档编辑器可能偏向差量和命令日志，配置中心可能偏向完整版本，流程引擎可能偏向检查点加事件。

Memento 和 Command 经常配合。Command 记录“做了什么”，Memento 记录“做之前是什么样”。撤销操作可以通过反向命令，也可以通过恢复快照。前者适合操作语义清晰的场景，后者适合状态复杂但快照成本可接受的场景。

生产系统还要处理敏感字段。快照里可能包含用户手机号、地址、密钥、合同内容。保存前要考虑脱敏、加密、访问控制、保留期限和删除机制。否则 Memento 会从可靠性工具变成数据合规风险。

### 4.7 Observer：观察者

**核心意图：** 当一个对象状态变化时，自动通知依赖它的对象。

Observer 是事件驱动架构的基础思想之一。

常见场景：

1. UI 状态更新；
2. 领域事件；
3. 缓存失效；
4. 消息发布订阅；
5. 配置变更通知；
6. 监控告警订阅。

Java 旧的 `Observable/Observer` API 已被弃用，官方文档提到它的事件模型有限，并建议在更丰富场景下考虑其他事件模型或并发相关 API。这个事实很有启发：Observer 不是“通知一下”这么简单。

在架构中使用 Observer，要明确这些问题：

| 问题 | 需要回答 |
|---|---|
| 同步还是异步 | 发布者是否等待订阅者完成。 |
| 顺序是否保证 | 多个订阅者是否有固定执行顺序。 |
| 失败如何处理 | 一个订阅者失败是否影响其他订阅者。 |
| 是否重试 | 异步事件失败后是否重试，重试多久。 |
| 是否幂等 | 重复事件是否会造成重复扣款、重复发货。 |
| 事务边界 | 事件是在事务前、事务中、还是事务后发布。 |

很多生产事故不是因为没有 Observer，而是因为 Observer 的事务、重试和幂等语义没有定义清楚。

Observer 的价值在于解耦“状态变化”和“后续反应”。订单支付成功后，发货、积分、短信、数据分析都可能关心这件事，但订单模块不应该直接调用所有后续模块。发布一个领域事件，让订阅方各自处理，是更稳的结构。

但 Observer 不是免费的异步魔法。同步观察者会影响主流程延迟和失败语义；异步观察者会引入最终一致性、重试、乱序和重复消费。设计时必须明确哪些订阅者是强一致要求，哪些只是旁路通知。

事件设计也很重要。事件应该描述已经发生的事实，而不是命令订阅者做什么。`OrderPaid` 比 `SendShippingMessage` 更像事件。事件内容要稳定，既不能太少导致订阅者回查过多，也不能暴露过多内部结构导致发布者难以演进。

生产级 Observer 通常需要配套 outbox、消息队列、幂等表、死信队列和监控。尤其当事件从进程内观察者升级为跨服务事件时，它已经进入事件驱动架构的范畴，必须按分布式系统来设计，而不是按回调函数来设计。

### 4.8 State：状态

**核心意图：** 让对象在内部状态改变时改变行为。

State 适合状态明确、状态行为差异大、状态迁移有规则的场景。

常见场景：

1. 订单状态；
2. 支付状态；
3. 工单状态；
4. 审批状态；
5. TCP 连接状态；
6. 播放器状态；
7. 工作流节点状态。

如果代码里到处都是：

```ts
if (order.status === 'PAID') {
	// ...
} else if (order.status === 'SHIPPED') {
	// ...
} else if (order.status === 'CANCELLED') {
	// ...
}
```

并且每个状态都有不同业务行为，就可以考虑 State。

State 的好处是把状态相关行为放到状态对象里。代价是状态类数量增加，而且迁移规则可能分散。复杂业务最好同时维护一份显式状态迁移表，方便产品、测试和开发一起审查。

State 适合状态本身决定行为的场景。订单在待支付、已支付、已发货、已取消时，对退款、发货、修改地址的响应完全不同。如果这些差异都写成 `if status`，业务会随着状态增加快速膨胀。把行为放进状态对象，可以让每个状态只关心自己的规则。

不过 State 不能只靠类来表达迁移。复杂业务里，状态迁移往往有角色、时间、库存、支付结果、风控结果等条件。状态对象可以实现行为，但最好仍有一张显式迁移表，用来说明从哪个状态可以到哪个状态、由什么事件触发、需要满足什么条件。

可以用这几个问题判断是否需要 State：

1. 同一个方法是否在不同状态下有明显不同行为；
2. 状态数量是否已经让条件分支难以维护；
3. 状态迁移是否需要被测试和审计；
4. 新增状态时是否希望局部新增代码，而不是修改大量 `switch`。

State 的误用是把简单枚举也拆成一堆类。比如只有 `enabled/disabled` 两种状态，并且只是控制一个按钮能否点击，枚举加条件判断更直接。只有当状态行为复杂、迁移规则重要时，State 才有足够收益。

### 4.9 Strategy：策略

**核心意图：** 定义一组算法，把它们封装起来，并让它们可以互相替换。

Strategy 是业务系统里最常用的设计模式之一。

常见场景：

1. 定价策略；
2. 折扣策略；
3. 路由策略；
4. 风控策略；
5. 推荐策略；
6. 重试策略；
7. 排序策略；
8. 压缩和加密算法。

Strategy 的架构价值是把“选择算法”和“执行算法”分开。

```ts
interface PricingStrategy {
	calculate(basePrice: number): number
}

class RegularPricing implements PricingStrategy {
	calculate(basePrice: number) {
		return basePrice
	}
}

class VipPricing implements PricingStrategy {
	calculate(basePrice: number) {
		return basePrice * 0.9
	}
}

function calculateOrderPrice(basePrice: number, strategy: PricingStrategy) {
	return strategy.calculate(basePrice)
}
```

Strategy 的难点通常不在策略类，而在策略选择。

如果策略由用户等级、地区、渠道、活动、实验分组、库存、时间共同决定，选择逻辑本身就需要规则表、配置中心或实验平台治理。否则策略类再优雅，系统仍然会乱。

Strategy 的核心是隔离“可替换算法”。在定价、推荐、路由、排序、重试、压缩、风控里，算法经常变化，但调用方不应该关心具体算法内部怎么做。调用方只依赖策略接口，策略选择由上下文或配置决定。

一个成熟 Strategy 设计通常分成两层：

1. 策略实现：每个策略只处理自己的算法；
2. 策略选择器：根据上下文选择合适策略。

很多系统的问题不在策略实现，而在选择器膨胀。比如价格策略由会员等级、城市、渠道、活动、库存共同决定，选择逻辑如果写成一长串 `if`，只是把复杂度从算法转移到了路由。这个时候需要规则引擎、决策表、实验平台或配置化优先级。

Strategy 和 Template Method 的区别在于变化位置。Strategy 替换整个算法对象；Template Method 固定算法骨架，只让部分步骤变化。如果流程结构不稳定，Strategy 更合适；如果流程骨架稳定，只是个别步骤差异，Template Method 或 pipeline 更合适。

误用 Strategy 的典型表现是每个策略只有一行代码，而且未来没有明确变化方向。抽象不是越早越好。先直接实现，等第二、第三种算法出现，并且差异方向清楚后再抽象，通常更稳。

### 4.10 Template Method：模板方法

**核心意图：** 在父类中定义算法骨架，把部分步骤延迟到子类实现。

Template Method 很适合框架代码。

例如一个导入流程固定为：

1. 校验文件；
2. 解析数据；
3. 校验记录；
4. 写入数据库；
5. 记录结果；
6. 发送通知。

不同导入类型只改解析和校验细节。这个时候模板方法可以保证主流程一致。

优点：

1. 主流程集中；
2. 子类只实现变化点；
3. 框架可以统一做日志、异常、事务和指标。

代价：

1. 依赖继承；
2. 子类可能依赖父类执行细节；
3. 钩子方法太多时，流程变得难以理解；
4. 父类修改可能影响所有子类。

现代代码中，很多 Template Method 可以用组合、回调函数、pipeline 或 higher-order function 替代。是否使用继承，要看项目已有风格和扩展点稳定性。

Template Method 的价值在于固定流程骨架。框架或父类控制执行顺序，子类只填充变化步骤。导入、导出、测试执行、请求处理、批处理任务都可能有固定骨架：准备资源、校验输入、执行业务、提交结果、处理异常、释放资源。

它最适合“流程稳定，步骤可变”的场景。如果主流程每天都在变，继承式模板会非常痛苦，因为父类改动会影响所有子类。如果只是某几个步骤变化，模板方法能保证所有实现都走同一套日志、事务、异常和指标逻辑。

设计 Template Method 时，要控制钩子数量。钩子太少，子类不得不绕过父类；钩子太多，父类流程变得难以理解。常见做法是把流程拆成少量明确步骤，例如 `validate()`、`parse()`、`persist()`、`afterCommit()`，每个步骤有清晰输入输出。

继承是 Template Method 的主要代价。现代代码里，可以用组合式 pipeline 替代继承：主流程接收几个回调或策略对象，而不是要求业务继承父类。这能降低继承耦合，也更方便测试。是否使用经典模板方法，取决于项目是否已经接受继承式扩展。

### 4.11 Visitor：访问者

**核心意图：** 在不改变对象结构的前提下，为对象结构增加新的操作。

Visitor 适合“对象结构稳定，但操作经常增加”的场景。

典型场景：

1. 编译器 AST；
2. 表达式树；
3. 规则树；
4. 文档节点树；
5. 报表结构；
6. 静态分析工具。

例如文档系统里有段落、标题、表格、代码块等节点。你可能需要增加 Markdown 导出、HTML 导出、字数统计、敏感词扫描、目录生成。若每个操作都写进节点类，节点类会越来越胖。Visitor 可以把这些操作拆出去。

Visitor 的权衡非常明确：

| 变化方向 | Visitor 是否适合 |
|---|---|
| 节点类型稳定，操作经常增加 | 适合 |
| 节点类型经常增加，操作相对稳定 | 不适合 |

因为每新增一个节点类型，所有 Visitor 都要补一个访问方法。这也是 Visitor 最大的维护成本。

Visitor 的核心是把“对象结构”和“作用在结构上的操作”分开。AST、文档树、表达式树这类结构往往有稳定节点类型，但操作会不断增加：格式化、导出、类型检查、统计、优化、扫描。把每个操作都塞进节点类，会让节点越来越重；Visitor 可以把操作拆成独立对象。

典型 Visitor 会让每个节点实现 `accept(visitor)`，然后回调 `visitor.visitParagraph(this)`、`visitor.visitTable(this)`。这样导出器、统计器、校验器都可以作为不同 Visitor 存在。节点类负责结构，Visitor 负责操作。

它的权衡很明确：新增操作容易，新增节点类型困难。比如文档系统新增一个 `ChartNode`，所有导出、统计、扫描 Visitor 都要处理它。这个成本不是缺点，而是设计选择。只有当节点类型相对稳定时，Visitor 才划算。

Visitor 还容易让操作跨越封装边界。为了让 Visitor 工作，节点可能暴露大量内部结构。更好的做法是暴露稳定只读接口，让 Visitor 读取必要信息，而不是直接修改节点内部状态。需要修改树结构时，可以单独设计 transformer，而不是让所有 Visitor 都有写权限。

## 5. 23 个模式在真实系统里如何一起工作

真实架构里，模式很少单独出现。它们通常组合在一起。

### 5.1 支付系统

一个支付模块可能这样组合：

| 模式 | 在支付系统里的位置 |
|---|---|
| Facade | 对外提供统一支付入口。 |
| Adapter | 适配支付宝、微信、Stripe 等外部 SDK。 |
| Abstract Factory | 为同一支付渠道创建支付、退款、验签、账单对象。 |
| Strategy | 选择路由、费率、风控、重试策略。 |
| Proxy | 包装远程支付调用，加入超时、日志、指标。 |
| Observer | 支付成功后发布领域事件，触发发货、通知、积分。 |
| Command | 把退款、补偿、异步确认封装成可重试任务。 |

这不是为了“展示模式”，而是因为支付系统确实存在外部渠道差异、异步事件、幂等、重试、监控和流程编排。

### 5.2 文档编辑器

一个文档编辑器可能这样组合：

| 模式 | 在文档编辑器里的位置 |
|---|---|
| Composite | 表示文档节点树。 |
| Command | 每次编辑操作封装成命令。 |
| Memento | 保存撤销重做快照。 |
| Visitor | 对文档树做导出、统计、扫描。 |
| Flyweight | 共享字体、样式、颜色等元数据。 |
| Iterator | 遍历文档节点或搜索结果。 |

这里的核心变化点是“文档结构复杂，操作很多，还要支持撤销”。

### 5.3 Web 框架请求链

一个 Web 请求处理框架可能这样组合：

| 模式 | 在请求链里的位置 |
|---|---|
| Chain of Responsibility | 组织认证、限流、日志、路由、中间件。 |
| Decorator | 为 handler 叠加缓存、指标、重试。 |
| Template Method | 固定请求处理骨架。 |
| Strategy | 替换路由算法、错误处理策略、降级策略。 |
| Proxy | 为远程服务客户端加入调用控制。 |

这里最重要的不是模式数量，而是执行顺序和错误语义。认证、限流、缓存、业务处理、异常处理、日志记录的顺序必须清楚。

## 6. 选择设计模式时的判断表

下面这张表可以作为实际项目中的快速判断。

| 遇到的问题 | 优先考虑 |
|---|---|
| 一组相关对象必须一起切换实现 | Abstract Factory |
| 对象构造参数很多、步骤复杂 | Builder |
| 框架需要把创建点留给扩展方 | Factory Method |
| 从模板复制新对象 | Prototype |
| 进程内只有一个共享实例 | Singleton，但优先考虑 DI 容器 |
| 外部接口和内部接口不一致 | Adapter |
| 两个变化维度都要独立扩展 | Bridge |
| 对象天然是树形结构 | Composite |
| 需要动态叠加横切能力 | Decorator |
| 子系统很复杂，需要简单入口 | Facade |
| 大量对象共享相同内部状态 | Flyweight |
| 需要控制真实对象访问 | Proxy |
| 请求要按顺序经过多个处理器 | Chain of Responsibility |
| 操作要排队、记录、撤销或重试 | Command |
| 要支持小型表达式或 DSL | Interpreter |
| 要隐藏集合内部遍历方式 | Iterator |
| 多对象交互太复杂 | Mediator |
| 要保存和恢复对象状态 | Memento |
| 状态变化要通知多个订阅者 | Observer |
| 不同状态下行为差异很大 | State |
| 算法需要可替换 | Strategy |
| 主流程固定，部分步骤变化 | Template Method |
| 对稳定对象结构增加新操作 | Visitor |

## 7. 常见误区

### 7.1 把模式当作目标

设计模式不是目标。可维护性、可测试性、可扩展性、低耦合、清晰边界才是目标。

如果一个普通函数可以解决问题，就不要为了“面向对象”拆出五个类。如果一个构造函数足够清楚，就不要强行 Builder。如果一个模块暂时只有一个实现，也不一定马上抽象工厂。

### 7.2 把所有变化都提前抽象

很多抽象不是来自真实变化，而是来自想象中的变化。想象变化最大的问题是：它经常猜错。

更务实的做法是：

1. 第一次直接实现；
2. 第二次出现相似逻辑时观察差异；
3. 第三次确认变化方向后再抽象。

当然，外部系统边界、支付、权限、安全、数据一致性这类高风险区域可以提前设计边界。但普通业务分支没必要一开始就模式化。

### 7.3 忽略模式的运行时成本

模式不仅有代码结构成本，也有运行时成本。

| 模式 | 容易忽略的成本 |
|---|---|
| Proxy | 远程调用、事务、懒加载被隐藏。 |
| Decorator | 包装层顺序影响语义。 |
| Observer | 异步失败、重试、幂等和事务边界复杂。 |
| Command | 命令版本兼容和重放语义复杂。 |
| Memento | 快照存储、隐私和恢复成本高。 |
| Composite | 深树遍历和循环引用风险。 |
| Visitor | 新增节点类型时改动面大。 |

### 7.4 模式名一样，实现却不一样

在现代语言和框架里，很多模式不再长得像 GoF 书里的类图。

例如：

1. Factory Method 可以是函数注册表；
2. Strategy 可以是函数对象；
3. Observer 可以是事件总线、消息队列或 reactive stream；
4. Proxy 可以由框架动态生成；
5. Singleton 可以由 DI 容器管理生命周期；
6. Template Method 可以由 pipeline 或 callback 实现。

所以不要只看形状，要看意图。

## 8. 结论

23 个 GoF 设计模式可以看成一套软件体系结构词汇。

创建型模式处理对象生命周期，结构型模式处理对象组合和模块边界，行为型模式处理对象协作和流程扩展。它们真正有价值的地方，不是让代码“看起来高级”，而是让变化被放在可预测、可测试、可替换的位置。

写代码时不要先问“这里能不能用某个模式”。更好的问题是：

1. 这里真正的变化点是什么；
2. 哪些依赖应该被隔离；
3. 哪些流程需要被扩展；
4. 哪些状态需要被保护；
5. 这个抽象会不会让下一个维护者更容易理解系统。

如果一个模式让这些问题更清楚，它就是有价值的。如果它只是增加类、接口和间接层，那它就是负担。
