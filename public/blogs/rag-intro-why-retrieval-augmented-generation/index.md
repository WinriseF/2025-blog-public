# RAG 入门：大模型为什么需要检索增强生成

---

RAG 是 Retrieval-Augmented Generation 的缩写，通常翻译为“检索增强生成”。它不是一个模型，也不是某一家厂商的产品，而是一种应用架构：在大模型回答前，先从外部知识源中检索相关资料，再把这些资料作为上下文交给模型生成答案。

---

## 1. 普通大模型调用的问题

直接调用大模型时，应用通常只给模型两类信息：

1. 系统提示词；
2. 用户当前问题。

这种方式适合通用问答、文本改写、代码解释、总结和简单推理。但一旦进入企业知识库、产品文档、法律条款、客服资料、内部规章等场景，就会暴露几个问题。

| 问题 | 说明 | 结果 |
|---|---|---|
| 知识过期 | 模型训练数据有时间边界，无法天然知道最新业务文档。 | 回答可能不是最新版本。 |
| 私有知识缺失 | 企业内部文档、数据库、工单、会议纪要不会出现在模型训练集中。 | 模型只能猜，不能基于真实资料回答。 |
| 幻觉 | 模型可能生成听起来合理但没有依据的内容。 | 用户难以判断答案是否可信。 |
| 上下文有限 | 即使模型支持长上下文，也不能每次塞入整个公司知识库。 | 成本高、速度慢、相关信息可能被稀释。 |
| 更新成本高 | 业务文档每天变化，不能每次变化都重新训练模型。 | 知识更新无法跟上业务。 |

RAG 的核心目标，就是把“模型参数里的静态知识”与“业务系统里的动态知识”连接起来。

---

## 2. RAG 是什么

RAG 可以拆成两个动作：

1. Retrieval：从外部知识源中检索和用户问题相关的内容；
2. Generation：把检索结果和用户问题一起交给大模型生成答案。

更具体地说，一个最基本的 RAG 系统会这样工作：

1. 先把文档导入系统；
2. 对文档进行清洗和切分；
3. 把每个文本片段转换成向量；
4. 把向量和原文片段存入向量数据库或搜索引擎；
5. 用户提问时，把问题也转换成向量；
6. 用问题向量检索最相似的文档片段；
7. 把这些片段拼进 Prompt；
8. 大模型基于检索到的上下文生成答案；
9. 系统返回答案，并尽量返回引用来源。

RAG 原始论文《Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks》提出的思想，是把预训练生成模型和可检索的非参数记忆结合起来，用外部知识增强知识密集型任务的表现。今天工程上的 RAG 不一定完全复现论文架构，但核心思想一致：模型不只依赖内部参数，而是在生成前检索外部知识。

---

## 3. RAG 和知识库问答是什么关系

很多人会把 RAG 等同于“知识库问答”。这在产品层面可以这么理解，但在工程层面不完全准确。

知识库问答是一个应用场景，RAG 是实现这个场景的常见架构。

| 名称 | 关注点 |
|---|---|
| 知识库问答 | 用户上传文档，然后向系统提问。 |
| RAG | 检索、上下文组装和大模型生成的技术流程。 |
| 语义搜索 | 根据语义相似度查找内容，不一定生成答案。 |
| Agentic RAG | 让 agent 决定是否检索、检索哪里、如何改写问题和组合工具。 |

一个系统可以只做语义搜索，不做 RAG。例如输入“报销发票规则”，系统只返回几个文档片段。

一个系统也可以做 RAG：输入“出差高铁票能不能报销”，系统检索到报销制度相关片段，然后生成一段自然语言回答，并给出引用。

## 4. RAG 和微调的区别

RAG 经常和微调混在一起。它们解决的问题不同。

| 方案 | 适合解决 | 不适合解决 |
|---|---|---|
| Prompt | 一次性任务约束、输出格式控制。 | 大规模私有知识注入。 |
| RAG | 让模型基于外部资料回答，资料可以频繁更新。 | 改变模型底层能力和稳定行为模式。 |
| 微调 | 调整模型风格、领域表达、特定任务模式。 | 高频更新的事实知识。 |
| 长上下文 | 临时处理单个长文档或少量资料。 | 大规模知识库、权限过滤、持续更新。 |

如果你的问题是“模型不知道我们公司的最新产品手册”，优先考虑 RAG。

如果你的问题是“模型总是不能按照我们公司的客服话术回答”，可以考虑 Prompt、RAG 和微调一起使用。

如果你的问题是“模型需要学习一个稳定的分类任务”，微调可能更合适。

## 5. RAG 的完整生命周期

RAG 不只是问答接口，它有两个阶段。

| 阶段 | 发生时间 | 核心任务 |
|---|---|---|
| 索引阶段 | 文档导入或更新时 | 加载、清洗、切分、向量化、入库。 |
| 查询阶段 | 用户提问时 | 问题处理、检索、重排、Prompt 组装、生成答案。 |

很多初学者只关注查询阶段，忽略了索引阶段。实际项目里，RAG 质量经常由索引阶段决定。

例如：

1. PDF 解析乱码，检索再强也没用；
2. Chunk 切得太碎，答案缺上下文；
3. Chunk 切得太大，检索不精准；
4. 元数据缺失，无法做权限过滤和引用；
5. 文档更新后没有同步删除旧向量，会答出旧制度。

RAG 的工程难点不是“调用一次模型”，而是把知识生命周期管理好。

## 6. 哪些场景适合 RAG

RAG 适合这些场景：

| 场景 | 为什么适合 |
|---|---|
| 企业知识库问答 | 文档多、内容私有、更新频繁。 |
| 客服助手 | 需要基于产品手册、FAQ、工单知识回答。 |
| 法务和合规查询 | 需要引用条款，不能凭空编。 |
| 技术文档助手 | SDK、API、部署文档内容多且版本变化快。 |
| 内部制度查询 | 员工手册、财务制度、采购流程适合按权限检索。 |
| 研究资料总结 | 需要先检索论文、报告、网页，再归纳回答。 |

RAG 不适合这些场景：

| 场景 | 原因 |
|---|---|
| 简单通用问答 | 直接调用模型就够了。 |
| 纯创意写作 | 外部检索可能限制创造性。 |
| 强事务操作 | RAG 只能提供知识，不能替代业务系统事务校验。 |
| 低质量资料库 | 检索到错误资料时，答案也会被污染。 |
| 权限边界不清晰的企业数据 | 没有权限控制就做 RAG，容易泄露资料。 |

一句话：RAG 的前提是你有一批值得检索、可以维护、权限清楚的资料。

## 7. 一个最小 RAG 系统需要哪些模块

最小可用 RAG 系统通常包含这些模块：

| 模块 | 职责 |
|---|---|
| 文档加载器 | 读取 PDF、Word、Markdown、网页、数据库记录。 |
| 文本清洗器 | 去掉页眉页脚、重复空白、乱码、无意义内容。 |
| Chunk 切分器 | 把长文档切成适合检索的片段。 |
| Embedding 模型 | 把文本变成向量。 |
| 向量存储 | 保存向量、原文、元数据并支持相似度检索。 |
| 检索器 | 根据用户问题找到相关片段。 |
| Prompt 模板 | 把问题和检索结果组合成模型输入。 |
| 生成模型 | 生成最终回答。 |
| 引用系统 | 返回文档来源、页码、章节或片段编号。 |
| 评测和日志 | 记录检索结果、答案质量、成本和延迟。 |

初学时可以先做简单版本：Markdown 文档、固定长度切分、OpenAI 或通义千问 Embedding、PostgreSQL + pgvector、一个问答接口。

后续再逐步加入混合检索、Rerank、权限控制和评测体系。

## 8. RAG 的常见误区

### 8.1 RAG 能彻底消除幻觉

不能。RAG 可以降低幻觉，但不能保证模型永远只说资料里有的内容。原因是检索可能失败，资料可能错误，Prompt 可能不严谨，模型也可能错误理解上下文。

更稳妥的做法是：

1. 要求模型只基于资料回答；
2. 没有证据时明确说不知道；
3. 返回引用；
4. 对高风险场景加入人工审核；
5. 用评测集持续回归。

### 8.2 向量数据库越强，RAG 就越好

向量数据库重要，但不是唯一核心。

RAG 质量来自整条链路：

1. 原始文档质量；
2. 解析质量；
3. Chunk 策略；
4. Embedding 模型；
5. 检索方式；
6. Rerank；
7. Prompt；
8. 生成模型；
9. 评测和反馈。

只换数据库，通常不能解决所有问题。

### 8.3 文档越多越好

不一定。低质量、重复、过期、互相矛盾的文档会降低检索质量。

企业 RAG 项目上线前，应该先做资料治理：

1. 删除过期文档；
2. 标记版本；
3. 合并重复资料；
4. 补充标题和元数据；
5. 建立文档责任人；
6. 设计更新和删除流程。

---

## 9. 总结

RAG 的本质是让大模型在回答前查资料。

它适合解决三类问题：

1. 模型知识过期；
2. 模型不知道私有资料；
3. 回答需要可追溯依据。

但 RAG 不是一个开关。一个真正可用的 RAG 系统，需要把文档解析、切分、向量化、检索、生成、引用、权限、评测和运维都纳入设计。
