# RAG 文档解析与 Chunk 切分：为什么答案质量经常坏在入库阶段

---

很多 RAG 项目一开始会把精力放在模型、向量数据库和框架上，但真正让答案变差的，经常是文档解析和 Chunk 切分。

这里专门记录索引阶段：一份文档进入系统前后，应该怎么解析、清洗、切分、补元数据，以及如何判断 Chunk 策略是否靠谱。

---

## 1. 文档解析不是读取字符串

RAG 系统需要的是可检索的知识单元，而不是文件原始文本。

直接把 PDF 或 Word 解析成一整段字符串，通常会丢掉这些信息：

1. 标题层级；
2. 页码；
3. 表格结构；
4. 列表关系；
5. 脚注；
6. 图片说明；
7. 版本号；
8. 权限范围；
9. 文档来源。

这些信息看起来像格式，实际会影响检索和引用。

例如用户问：

```text
试用期员工可以报销差旅费吗？
```

如果 Chunk 只保存正文“可以报销”，却丢掉标题“正式员工差旅政策”，模型就可能错误回答。标题和章节是语义上下文，不是装饰。

---

## 2. 不同文档类型的处理方式

不同文档类型不能用同一种解析策略。

| 类型 | 解析重点 | 常见问题 |
|---|---|---|
| Markdown | 保留标题层级、代码块、表格。 | 切分时破坏标题和正文关系。 |
| PDF | 保留页码、段落顺序、表格。 | 页眉页脚重复、分栏错序、扫描件 OCR 错误。 |
| Word | 保留标题、列表、表格、批注取舍。 | 样式和真实层级不一致。 |
| HTML | 提取正文，删除导航、广告、脚本。 | 页面模板噪声多。 |
| Excel | 按表、行、列解释语义。 | 不能直接把所有单元格拼成一段。 |
| 数据库记录 | 字段名和字段值一起入库。 | 只存值会丢字段语义。 |

文档解析的目标是还原语义结构。

例如数据库记录不要只入库：

```text
二等座 可以 员工
```

应该入库：

```text
制度名称：差旅报销制度
适用对象：员工
交通工具：高铁二等座
是否可报销：可以
```

字段名本身就是检索语义的一部分。

---

## 3. 文本清洗要保守

清洗不是把文本改得越短越好，而是去掉明显噪声，同时保留可解释信息。

建议删除：

1. 重复页眉页脚；
2. 页面编号；
3. 导航菜单；
4. 广告语；
5. 多余空白；
6. 解析错误产生的孤立字符；
7. 和正文无关的版权模板。

建议保留：

1. 标题；
2. 小标题；
3. 列表编号；
4. 表格字段名；
5. 页码；
6. 文档版本；
7. 生效日期；
8. 适用范围；
9. 例外条款。

清洗过度会导致答案缺少限制条件。

例如原文：

```text
员工出差可报销高铁二等座。试用期员工需经部门负责人审批后报销。
```

如果清洗或切分时只保留第一句，系统会对试用期员工给出错误回答。

---

## 4. Chunk 的本质是检索单元

Chunk 不是随便切出来的文本块，而是系统检索和引用的基本单位。

一个好的 Chunk 应该满足：

1. 能独立表达一个相对完整的意思；
2. 不超过模型上下文和 Embedding 模型限制；
3. 包含足够标题和来源信息；
4. 可以被用户引用和核对；
5. 适合被 Rerank 模型判断相关性；
6. 权限边界清晰。

如果一个 Chunk 需要依赖前后好几段才能理解，它可能太碎。

如果一个 Chunk 包含三个无关主题，它可能太大。

---

## 5. 固定长度切分

固定长度切分是最简单的方式。

例如每 1000 个字符切一段，overlap 200 个字符。

优点：

1. 实现简单；
2. 适合快速 Demo；
3. 对纯文本资料效果尚可；
4. 参数容易控制。

缺点：

1. 可能切断句子；
2. 可能切断表格；
3. 标题和正文关系可能丢失；
4. 不理解文档结构。

适合场景：

1. 文档结构不清晰；
2. 先做原型；
3. 语料主要是连续文本；
4. 没有复杂表格和章节。

不适合场景：

1. 法律条款；
2. 技术 API 文档；
3. 财务制度；
4. 表格密集资料；
5. 标题层级非常重要的文档。

---

## 6. 按标题层级切分

结构化文档优先按标题切分。

例如 Markdown：

```text
标题：差旅报销制度
一级章节：交通费用
二级章节：高铁
正文：员工出差可报销高铁二等座。
```

生成 Chunk 时应该保留标题路径：

```json
{
	"content": "员工出差可报销高铁二等座。",
	"metadata": {
		"title_path": "差旅报销制度 > 交通费用 > 高铁"
	}
}
```

标题路径可以在两个地方发挥作用：

1. 进入 Embedding 文本，提高检索命中率；
2. 作为元数据返回给用户，提高引用可读性。

实际入库文本可以拼成：

```text
差旅报销制度 > 交通费用 > 高铁
员工出差可报销高铁二等座。
```

这比只嵌入正文更可靠。

---

## 7. 滑动窗口和 overlap

Overlap 用来减少切分边界带来的信息丢失。

例如 chunk size 1000、overlap 200，意味着相邻 Chunk 共享一部分文本。

优点：

1. 避免关键句刚好被切断；
2. 保留上下文连续性；
3. 提高召回概率。

缺点：

1. 增加向量数量；
2. 增加存储成本；
3. 检索结果更容易重复；
4. Rerank 前需要去重。

Overlap 不是越大越好。经验上可以从 10% 到 20% 开始，再根据评测调整。

如果文档本身按标题切分很好，overlap 可以小一些。如果是连续叙述文本，overlap 可以适当增大。

中文资料还要额外注意分隔符。LangChain 的递归字符切分器默认会优先按空行、换行、空格等分隔，英文文本通常还可以，但中文、日文、泰文这类没有天然空格分词的语言，可能把词或短语切断。处理中文知识库时，建议在分隔符里显式加入中文句号、逗号、顿号、全角标点等，或者优先按标题、段落和语义结构切分。

---

## 8. Parent-Child Chunk

Parent-Child Chunk 是一种常见改进策略。

做法：

1. Child Chunk 较小，用于精确检索；
2. Parent Chunk 较大，用于提供完整上下文；
3. 检索命中 Child 后，把对应 Parent 或相邻片段提供给模型。

适合场景：

1. 文档章节较长；
2. 小片段检索更准，但回答需要完整段落；
3. 技术文档和政策文档；
4. 问题常涉及上下文限制条件。

示例：

| 层级 | 内容 |
|---|---|
| Parent | 差旅报销制度 > 交通费用整节 |
| Child | 高铁二等座报销规则 |

用户问“高铁二等座能报吗”时，Child 更容易被命中。生成答案时，系统可以把 Parent 中的限制条件一起带上，避免漏掉“试用期需审批”。

---

## 9. 表格如何切分

表格是 RAG 难点。

错误做法是把表格直接解析成空格分隔文本：

```text
交通工具 标准 是否报销 高铁 二等座 是 飞机 经济舱 是 专车 无 否
```

更好的方式是按行转成语义句：

```text
差旅报销制度中，交通工具为高铁时，报销标准为二等座，是否可报销：是。
差旅报销制度中，交通工具为飞机时，报销标准为经济舱，是否可报销：是。
差旅报销制度中，交通工具为专车时，报销标准为无，是否可报销：否。
```

如果表格很大，可以：

1. 表头作为上下文；
2. 每行或多行组成 Chunk；
3. 保留表格名称；
4. 保留行号；
5. 对数值类查询考虑结构化数据库查询，而不是只靠 RAG。

RAG 不擅长精确计算和复杂表格推理。遇到预算、金额、库存、账单这类问题，应该考虑 Text-to-SQL 或工具调用。

## 10. 元数据设计

元数据是 RAG 生产化的基础。

建议每个 Chunk 至少包含：

| 字段 | 用途 |
|---|---|
| chunk_id | 唯一定位片段。 |
| document_id | 关联原始文档。 |
| source | 文件名、URL 或数据库来源。 |
| title | 文档标题。 |
| title_path | 标题层级路径。 |
| page | 页码或位置。 |
| version | 文档版本。 |
| effective_date | 生效日期。 |
| owner | 文档责任团队。 |
| permission_key | 权限过滤。 |
| content_hash | 判断内容是否变化。 |

不要等上线后再补元数据。没有元数据，后续会很难做权限、引用、更新、删除和评测。

---

## 11. Chunk 策略怎么评估

不要只凭感觉判断 Chunk 好不好。可以建立一个小型测试集。

测试集格式：

```json
{
	"question": "试用期员工出差坐高铁二等座可以报销吗？",
	"expected_sources": ["expense-policy-2026"],
	"expected_answer_points": ["可以报销", "需要部门负责人审批"]
}
```

评估时先不看最终答案，只看检索结果：

1. 正确文档是否进入 Top K；
2. 正确 Chunk 是否进入 Top K；
3. 限制条件是否被检索到；
4. 检索结果是否重复；
5. 无关 Chunk 比例是否过高。

如果正确 Chunk 没进 Top K，问题通常在解析、切分、Embedding 或检索策略。

如果正确 Chunk 进了 Top K，但答案错，问题通常在 Prompt、上下文组装或生成模型。

## 12. 推荐起步策略

不同资料可以这样起步：

| 文档类型 | 起步策略 |
|---|---|
| Markdown 技术文档 | 按标题切分，标题路径进入内容。 |
| PDF 制度文档 | 先清洗页眉页脚，再按标题或段落切分。 |
| Word 文档 | 保留标题和列表，按章节切分。 |
| FAQ | 一问一答作为 Chunk。 |
| 表格 | 按行转语义句，保留表头和表名。 |
| 工单记录 | 按问题、处理过程、结论拆分。 |
| API 文档 | 按接口或参数小节切分。 |

初始参数可以保守一点：

1. 普通说明文档：800 到 1200 字符；
2. 技术文档：按标题，小节过长再二次切分；
3. overlap：10% 到 20%；
4. Top K：先从 5 到 8 试起；
5. 所有 Chunk 带标题路径。

这些不是标准答案，只是启动配置。最终要通过评测确定。

---

## 13. 总结

RAG 的答案质量经常坏在入库阶段。

一个好的文档处理流程应该做到：

1. 文档解析保留语义结构；
2. 文本清洗去噪但不过度删除；
3. Chunk 能独立表达相对完整意思；
4. 标题路径进入 Chunk；
5. 表格转成可检索语义；
6. 元数据从第一天就设计好；
7. 用测试集评估 Chunk 策略。
