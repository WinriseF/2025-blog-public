## 2. AI 大模型是什么

AI 大模型是指通过超大规模参数和海量数据训练得到的深度学习模型。它能够理解和生成人类语言，并逐步扩展到图像、音频、视频等多模态数据处理能力，表现出较强的推理、生成和创作能力。

可以从四个方面理解大模型的特点：

| 特点 | 说明 |
|---|---|
| 参数规模大 | 模型通常拥有数十亿到数万亿级别参数。 |
| 训练数据多 | 依赖海量文本、图像、代码、音频、视频等数据训练。 |
| 生成能力强 | 可以生成文本、代码、图片、摘要、方案、报告等内容。 |
| 推理能力强 | 可以拆解复杂任务、规划步骤、调用工具并完成较复杂的问题求解。 |

大模型能力的发展不是线性的。随着模型规模、训练数据、工具调用能力、知识库能力和智能体能力增强，AI 会逐步从简单问答走向复杂任务执行。

## 3. 主流大模型生态

当前大模型生态已经进入百花齐放阶段，常见厂商和模型包括：

| 厂商 / 组织 | 代表模型或产品 | 说明 |
|---|---|---|
| OpenAI | GPT 系列、GPT-4o 等 | 通用能力强，生态成熟。 |
| Anthropic | Claude 系列 | 长上下文、代码和文档处理能力较强。 |
| Google | Gemini 系列 | 多模态能力突出。 |
| Meta | Llama 系列 | 重要的开源模型生态。 |

| 阿里云 | 通义千问 / Qwen、百炼、DashScope | 国内常见的大模型服务和应用开发平台。 |

开发者需要具备模型选型能力，而不是只会使用某一个固定模型。不同模型在准确率、速度、成本、上下文长度、多模态、工具调用和生态支持方面都有差异。

## 4. 大模型的四种分类方式

### 4.1 按模态分类

| 类型 | 说明 | 示例 |
|---|---|---|
| 单模态模型 | 主要处理文本。 | 早期 GPT-3 等。 |
| 多模态模型 | 可以处理文本、图像、音频、视频等多种数据。 | GPT-4o、Gemini 等。 |
| 原生多模态模型 | 模型内部原生支持多种模态，不需要用户显式切换模型。 | 新一代多模态大模型的发展方向。 |

多模态是未来主流趋势。用户只需要自然表达需求，模型可以自动决定输出文本、图片、音频或其他形式的内容。

### 4.2 按开源性分类

| 类型 | 特点 | 适合场景 |
|---|---|---|
| 闭源模型 | 由厂商维护，能力和稳定性通常较强。 | 快速开发、商业应用、云端调用。 |
| 开源模型 | 可本地部署、可微调、可控性强。 | 私有化部署、数据安全、研究学习、行业定制。 |

企业如果要自部署模型，建议优先选择社区活跃、文档完善、Star 数较多、生态成熟的开源模型。

### 4.3 按模型规模分类

| 类型 | 特点 | 适合场景 |
|---|---|---|
| 小模型 | 成本低、速度快、硬件要求低。 | 简单分类、翻译、轻量问答。 |
| 中等模型 | 能力和成本相对平衡。 | 普通业务应用。 |
| 大模型 | 复杂推理和生成能力更强，但成本更高。 | 智能体、复杂分析、代码生成、长文档处理。 |

模型不是越大越好。简单任务使用超大模型可能造成性能和成本浪费。技术选型时应优先匹配业务需求。

### 4.4 按用途分类

| 类型 | 说明 | 示例 |
|---|---|---|
| 通用大模型 | 可以处理广泛问题，但在特定领域不一定最专业。 | GPT、Claude、Gemini、Qwen 等。 |
| 垂直领域模型 | 针对某个行业或场景做过专项优化。 | 法律模型、医疗模型、金融模型、编程模型等。 |

垂直领域模型通常以通用大模型为基础，再结合行业数据进行训练、微调或知识增强，因此在特定领域可能比通用模型更可靠。

## 5. 开发者应该重点学习什么

普通 AI 应用开发者短期内不需要优先深入研究大模型训练细节，例如 Transformer 架构、预训练过程、底层参数优化等。这些内容更偏算法研究或模型训练方向。

应用开发者更应该重点掌握以下能力：

| 能力 | 说明 |
|---|---|
| 模型选型 | 根据准确率、功能、速度、成本、安全等维度选择模型。 |
| API 调用 | 在业务系统中通过 API 调用大模型。 |
| SDK 使用 | 使用官方 SDK 或第三方 SDK 集成模型服务。 |
| AI 开发框架 | 掌握 Spring AI、LangChain4j 等框架，降低模型切换成本。 |
| Prompt Engineering | 设计系统提示词、用户提示词、模板变量和输出格式。 |
| 上下文管理 | 管理多轮对话、历史记忆、上下文长度和会话状态。 |
| RAG 知识库 | 将企业资料、业务文档、知识库提供给 AI 查询。 |
| 工具调用 | 让模型调用外部函数、接口、数据库、搜索引擎等工具。 |
| MCP 服务 | 通过标准化协议扩展模型可调用的外部能力。 |
| 部署与运维 | 完成应用上线、监控、告警、成本控制和持续优化。 |
| 安全与合规 | 关注数据隐私、内容安全、服务备案和行业合规要求。 |

## 6. AI 应用开发工作流

AI 应用开发可以理解为传统软件开发流程叠加模型能力、提示词、知识库和工具调用等 AI 特性。

![大模型应用开发工作流](/blogs/ai-large-model-access-intro-1/1.png)

### 6.1 需求分析与模型选择

首先需要明确业务目标：

- 要解决什么问题？
- 是否需要文本、图片、音频或视频处理？
- 是否需要强推理能力？
- 是否需要知识库？
- 是否需要工具调用或 MCP 服务？
- 是否有数据安全、合规或私有化部署要求？
- 成本预算是多少？

### 6.2 开发环境搭建

包括：

- 初始化后端项目；
- 开通大模型服务；
- 获取 API Key；
- 配置 SDK 或 AI 开发框架；
- 完成基础模型调用逻辑。

### 6.3 Prompt 设计

Prompt 设计包括：

- 系统提示词；
- 用户提示词模板；
- 变量填充；
- 角色设定；
- 输出格式约束；
- 多轮对话上下文管理；
- 对话记忆设计。

### 6.4 AI 应用功能开发

包括：

- 业务核心逻辑；
- 用户界面；
- 知识库接入；
- 工具调用；
- MCP 服务；
- 工作流编排；
- 智能体任务规划。

### 6.5 测试、部署与运维

AI 应用上线前后需要关注：

- 功能测试；
- 回答质量测试；
- 幻觉问题处理；
- 日志和调用链追踪；
- 成本监控；
- 服务稳定性；
- 异常告警；
- 部署到服务器或 Serverless 平台。

### 6.6 持续迭代优化

AI 应用通常不是一次开发完成，而是需要持续迭代：

> 上线验证 → 收集反馈 → 优化 Prompt / 模型 / 知识库 / 工具 → 再次上线。

## 7. 如何选择合适的大模型

模型选型可以从以下维度评估：

| 维度 | 需要关注的问题 |
|---|---|
| 功能支持 | 是否支持文本、图像、音频、视频、代码、多模态、工具调用。 |
| 上下文长度 | 能否处理长文本、长文档、多轮会话历史。 |
| 指令遵循能力 | 能否准确执行复杂指令，是否容易跑偏。 |
| 输出质量 | 回答是否准确、完整、可靠，幻觉是否严重。 |
| 响应速度 | 首字延迟、整体生成速度、并发能力。 |
| API 与 SDK | 是否提供稳定 API、示例代码和多语言 SDK。 |
| 框架兼容性 | 是否被 Spring AI、LangChain4j 等框架支持。 |
| 成本价格 | Token 单价、免费额度、批量调用成本。 |
| 稳定性 | 服务可用性、限流策略、故障率。 |
| 数据安全 | 是否支持私有化部署、数据隔离、权限控制。 |
| 法律合规 | 是否满足所在地区和行业的监管要求。 |
| 生态成熟度 | 文档是否完善，社区是否活跃，问题是否容易解决。 |

对于多数开发者，可以优先记住四个核心指标：

| 核心指标 | 判断问题 |
|---|---|
| 准不准 | 输出质量是否可靠？幻觉是否可控？ |
| 功能够不够 | 是否支持多模态、RAG、工具调用、MCP 等需求？ |
| 快不快 | 响应速度和并发能力是否满足业务要求？ |
| 贵不贵 | 调用成本是否在预算范围内？ |

模型选型不是选择“最强模型”，而是选择在准确率、功能、速度、成本之间最适合当前业务的模型。

## 8. 云服务与本地部署

使用大模型通常有两种方式：使用云服务，或自行部署模型。

### 8.1 使用云服务

云服务是个人开发者和多数学习项目的优先选择。

| 优点 | 说明 |
|---|---|
| 快速可用 | 无需自行部署模型和算力环境。 |
| 稳定性高 | 由云厂商维护基础设施。 |
| 按需付费 | 用多少付多少，不需要提前购买高性能服务器。 |
| 模型更新快 | 更容易接入新版本模型。 |
| 安全合规相对完善 | 大厂通常会提供较完善的安全和合规能力。 |

适合场景：

- 个人学习；
- 快速原型验证；
- 小型业务应用；
- 对私有化要求不高的项目。

### 8.2 本地部署 / 私有化部署

本地部署是将模型代码、权重和运行环境部署到自己的电脑、服务器或企业内网中。

| 优点 | 说明 |
|---|---|
| 数据更安全 | 数据不需要发送到第三方平台。 |
| 可控性更强 | 可以微调、定制和管理模型。 |
| 减少厂商绑定 | 不完全依赖某一家云厂商。 |
| 内网访问延迟较低 | 在特定场景下可以减少网络传输成本。 |

主要缺点：

- GPU 和服务器成本高；
- 运维复杂；
- 需要专业团队维护；
- 模型更新和效果优化成本高；
- 小模型能力可能无法达到云端大模型水平。

适合场景：

- 大型企业；
- 数据安全要求很高的业务；
- 行业模型定制；
- 实验室和研究场景；
- 内部数据不能外传的场景。

结论：个人开发者优先使用云服务。只有在数据安全、行业定制或企业级私有化要求明确时，才优先考虑本地部署。

## 9. 接入大模型的三种方式

### 9.1 通过 AI 应用平台接入

代表平台包括阿里云百炼、Dify、Coze 等。

这类平台通常提供：

- 模型广场；
- 在线模型体验；
- Prompt 调试；
- 智能体应用；
- 工作流编排；
- 知识库管理；
- 应用评测；
- 应用观测；
- API 发布能力。

优点是低代码或无代码，适合快速搭建 AI 应用。即使不熟悉编程，也可以通过可视化配置完成智能客服、知识库问答、内容生成等应用。

### 9.2 通过 AI 客户端接入

常见客户端包括 Cherry Studio 和 Cursor。

| 工具 | 定位 | 适合场景 |
|---|---|---|
| Cherry Studio | 多模型 AI 对话客户端 | 日常对话、模型调试、本地模型接入、MCP 配置。 |
| Cursor | AI 编程工具 | 代码生成、项目改造、代码解释、智能体式编程。 |

Cursor 支持 Ask 模式和 Agent 模式：

- Ask 模式适合普通问答；
- Agent 模式适合让 AI 自主规划、修改代码、生成文件、完成复杂开发任务。

### 9.3 通过代码接入

程序接入是开发者最重要的能力，主要分为两种路线：

#### 路线一：直接调用大模型 API

开发者直接调用模型厂商提供的 API，例如通义千问、DeepSeek、OpenAI、Claude、Gemini 等。

优点：

- 更底层；
- 更灵活；
- 更适合企业深度定制；
- 可以自行控制 Prompt、上下文、工具调用、知识库和业务逻辑。

缺点：

- 需要自行处理更多工程细节；
- 代码量和维护成本较高。

#### 路线二：调用平台创建好的应用或智能体

流程通常是：

1. 在平台中创建智能体、工作流或应用；
2. 配置模型、Prompt、知识库、工具和 MCP；
3. 发布应用；
4. 在代码中通过 API 和应用 ID 调用该应用。

优点：

- 开发速度快；
- 代码少；
- 很多能力由平台封装；
- 适合小公司或快速上线场景。

缺点：

- 灵活性不如直接调用模型；
- 更依赖平台能力；
- 平台迁移成本可能较高。

建议：小型项目可以优先调用平台应用；企业级复杂项目应学习直接调用模型，并结合 Spring AI、LangChain4j 等框架提升可维护性。

## 10. 阿里云百炼与 DashScope

### 10.1 阿里云百炼

阿里云百炼是一站式大模型应用开发平台，可以用于：

- 体验和调用模型；
- 调试 Prompt；
- 创建智能体应用；
- 创建工作流应用；
- 创建智能体编排应用；
- 管理知识库；
- 发布 API；
- 观测应用调用情况。

百炼更偏向可视化应用构建平台。

### 10.2 DashScope / 灵积

DashScope 是阿里云提供的大模型调用服务，也可以理解为程序访问阿里云大模型能力的 API 层。

二者关系可以理解为：

| 名称 | 定位 |
|---|---|
| 阿里云百炼 | 可视化大模型应用开发平台。 |
| DashScope / 灵积 | 面向程序调用的大模型服务与 API。 |

百炼平台底层会涉及模型调用能力，而开发者在代码中调用阿里云大模型时，通常会接触到 DashScope 相关 API、SDK 或配置。

## 11. 阿里云百炼的三种应用形态

### 11.1 智能体应用

智能体应用可以理解为一个简单的 AI 助手，适合对话类应用。

典型场景：

- 智能客服；
- 知识库问答；
- 恋爱咨询助手；
- 编程问答助手；
- 企业内部助理。

核心配置包括：

- 选择模型；
- 设置系统提示词；
- 配置变量；
- 接入知识库；
- 开启联网搜索；
- 配置工具或 MCP 服务；
- 发布 API 或其他渠道。

### 11.2 工作流应用

工作流应用适合流程明确、步骤可控的任务。它像一条流水线，每个节点完成一个明确动作。

示例流程：

1. 用户输入城市和日期；
2. 大模型根据输入生成天气查询结果；
3. 输出结果；
4. 可进一步转换为 PDF、语音、报告或其他格式。

工作流的主体是节点。节点可以是：

- 大模型；
- 条件判断；
- 脚本处理；
- 文本转换；
- 文件生成；
- 插件调用；
- 外部接口调用。

适合场景：

- 固定业务流程；
- 文档生成；
- 内容审核；
- 数据处理；
- 自动化办公。

### 11.3 智能体编排应用

智能体编排应用适合复杂任务和多智能体协作。它的核心不是普通节点，而是多个智能体之间的协同。

示例：

1. 一个智能体分析用户需求；
2. 一个智能体搜索资料；
3. 一个智能体生成方案；
4. 一个智能体检查和优化结果；
5. 最后汇总输出。

适合场景：

- 风险评估；
- 投资组合分析；
- 研报生成；
- 多步骤业务决策；
- 强依赖 AI 判断的复杂任务。

三种应用形态对比如下：

| 类型 | 核心 | 适合场景 | 可控性 | 灵活性 |
|---|---|---|---|---|
| 智能体应用 | 单个 AI 助手 | 问答、客服、简单助手 | 中 | 中 |
| 工作流应用 | 固定流程节点 | 文档生成、流程自动化 | 高 | 中 |
| 智能体编排应用 | 多智能体协作 | 复杂分析、任务规划 | 中 | 高 |

简单判断：

- 只需要一个 AI 助手：用智能体应用；
- 明确知道每一步流程：用工作流应用；
- 希望多个 AI 专家协作并自主判断：用智能体编排应用。

## 12. Spring AI 与 LangChain4j

在 Java 项目中，可以使用 Spring AI、Spring AI Alibaba 或 LangChain4j 来接入大模型。

这些框架的核心价值是统一不同模型厂商的调用方式，降低代码与特定厂商的耦合。

如果直接使用某个平台的 SDK，后续从阿里云切换到 DeepSeek、OpenAI 或其他模型时，可能需要修改大量代码。使用 AI 开发框架后，很多能力可以通过统一接口和配置来完成。

常见能力包括：

- Chat 模型调用；
- Embedding 向量模型调用；
- 多模态输入；
- 流式响应；
- 函数调用 / 工具调用；
- RAG 知识库；
- 可观测能力；
- 多模型切换。

选型时应查看框架官方文档，确认目标模型是否支持以下能力：

- 工具调用；
- 多模态；
- 流式响应；
- JSON 输出；
- 自定义客户端；
- 本地模型接入；
- 可观测能力。

当前开发 AI 应用时，不建议选择完全不支持工具调用的模型。工具调用已经成为智能体和复杂 AI 应用的基础能力之一。

---

## 13. 大模型能力边界与常见问题

开发者需要理解大模型能做什么，也要知道它不能稳定做什么。

常见问题包括：

| 问题 | 说明 | 处理思路 |
|---|---|---|
| 幻觉 | 模型生成看似合理但实际错误的内容。 | 引入 RAG、工具校验、结果审核。 |
| 知识过期 | 模型训练数据不一定包含最新信息。 | 接入联网搜索或业务知识库。 |
| 上下文限制 | 输入内容超过模型上下文长度会丢失信息。 | 做文档切分、摘要、检索增强。 |
| 指令跑偏 | 模型没有严格遵守要求。 | 优化系统提示词和输出格式约束。 |
| 成本不可控 | 高频调用大模型可能造成较高费用。 | 缓存、模型分级、限流、压缩上下文。 |
| 安全风险 | 可能泄露敏感数据或产生不合规内容。 | 权限控制、脱敏、内容审核、私有化部署。 |

关于 MCP，需要注意：大模型不是直接调用你的服务器资源，而是通过你的程序、服务或中间层进行转发和协议化调用。开发者需要设计好工具暴露方式、权限边界和调用流程。

## 14. 推荐学习路径

建议按照以下顺序学习：

1. 理解大模型基本概念和分类；
2. 学会使用 AI 应用平台体验模型；
3. 学会使用 Cherry Studio、Cursor 等工具提升效率；
4. 学会通过 API 调用大模型；
5. 学习 Spring AI 或 LangChain4j；
6. 学习 Prompt Engineering；
7. 学习 RAG 知识库；
8. 学习工具调用；
9. 学习 MCP 服务；
10. 学习智能体规划、工作流和多智能体编排；
11. 学习部署、监控、评测与持续优化。

推荐实践路线：

> 平台体验 → API 调用 → AI 开发框架 → Prompt 优化 → RAG → 工具调用 → MCP → 智能体项目实战。

## 17. 最终结论

本节内容的核心结论可以概括为：

1. 开发者应优先掌握大模型应用开发能力，而不是一开始深挖训练原理。
2. 模型选型要综合考虑准确率、功能、速度和成本。
3. 个人开发者优先使用云服务，企业在数据安全要求高时考虑私有化部署。
4. AI 应用平台适合快速搭建和验证，代码接入适合深度定制和企业级开发。
5. Spring AI、LangChain4j 等框架可以降低模型厂商切换成本。
6. RAG、工具调用、MCP、工作流和智能体编排，是后续 AI 智能体开发的关键能力。
7. AI 应用需要持续迭代，持续优化 Prompt、模型、知识库、工具和成本控制策略。

这节课可以作为后续学习 AI 超级智能体项目的基础认知章节。后续重点应逐步进入后端项目初始化、模型 API 调用、Spring AI 集成、知识库、工具调用、MCP 服务和智能体开发实战。
